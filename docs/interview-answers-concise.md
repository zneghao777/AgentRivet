# AI Agent 面试问答（项目版）

基于 MyAgentDemo1 当前源码，核对日期：2026-09-03。
参数均为代码默认值；“待完善”不代表已实现，配置容量不代表压测结果。

## 1. 模型或 RAG 幻觉怎么解决？

先定位幻觉发生在哪一层，再处理对应问题。

| 问题 | 怎么判断 | 怎么处理 |
| --- | --- | --- |
| 知识源错误或过期 | 原文就不正确，或存在多个冲突版本 | 治理来源、版本和更新时间，重建索引 |
| 检索没找到正确证据 | 正确原文存在，但召回结果里没有 | 检查解析、切分、关键词召回和查询表达 |
| 证据被截断或噪声过多 | 已召回，但送给模型的内容不完整或不相关 | 重排序、去重，保留必要上下文 |
| 模型超出证据作答 | 证据正确，回答却增加了不存在的结论 | 约束引用、补查或拒答，校验关键结论 |

项目已有混合检索、重排序和分块引用，可通过 Trace 回查工具结果。
进一步应校验“引用是否真的支持结论”，并把失败样本加入回归集。
**低 temperature、有引用都不保证没有幻觉**；线上统一的证据充分性判断和事实核验仍待完善。

## 2. 意图识别怎么做？

项目分三层，不能统称为一个分类模型。

- **工具选择**：主模型根据消息、上下文和工具描述生成 `tool_calls`。
- **Agent 路由**：开启多 Agent 后，过滤不可用或已熔断的候选，Router 读取能力卡和最近上下文，输出目标、模式及置信度；Pydantic 校验，失败重试一次再回退主 Agent。
- **检索路由**：根据关系类关键词和图谱就绪状态，选择文本或融合检索。

Router 默认置信度低于 `0.5` 时澄清；这是模型自评分，不是校准后的正确概率。
上下文必须参与识别，例如用户补充“2030”可能是在回答年份，不能仅根据最后一句重新分类。
评测时应同时看路由正确率、澄清率，以及普通续聊被误派给专用 Agent 的比例。

## 3. RAG 怎么评测？怎么看好坏？

分检索、回答、运行三层，使用固定数据集对比方案。

| 层次 | 指标 | 当前实现 |
| --- | --- | --- |
| 检索 | HitRate@K：是否命中；MRR@K：首个命中的排名 | 已实现 |
| 回答 | Faithfulness、Relevancy，分别评 1～5 分 | 可选 LLM judge |
| 补充评测 | Recall、Precision、nDCG、答案正确性、拒答与引用正确率 | 需要补齐 |
| 运行 | P95 延迟、错误率、单次成本 | 有观测基础，需结合压测 |

项目对比纯向量、混合检索、混合检索加重排序，并保存每个用例的命中和排序结果。
`MRR = mean(1 / 首个正确结果排名)`，未命中记 0。
例如首个正确结果排第 1、第 3、未命中，则 MRR 为 `(1 + 1/3 + 0) / 3`。

**几个指标不能混淆：** HitRate 只要求至少命中一条；Recall 关心必要证据是否找全；
MRR 关心第一个正确结果是否靠前。多跳问题命中一条并不代表能回答完整。
Faithfulness 衡量是否忠实于资料，答案正确性还要与可信的标准答案核对。

实际评测可以这样组织：

1. 从业务问题构建数据集，标注答案及必要证据，覆盖精确查找、语义表达、多跳、冲突和无答案问题。
2. 固定知识版本和模型，分别调整召回、重排序、Top-K 等因素，比较效果、延迟和成本。
3. 对失败样本分层归因，人工抽查 judge 结果；保留独立测试集，避免只对调参样本有效。

**边界**：当前 judge 使用最后一个方案的上下文，有 `reference_answer` 就直接评该答案；
没有完整重放线上 Agent 链路。文档级命中也比证据分块级命中宽松，
当前用例校验对无答案问题的支持还需扩展。因此已有评测能力，不等于已有生产准确率结论。

## 4. ReAct、死循环与重新检索

ReAct 是“推理 → 行动 → 观察结果 → 再决策”。项目链路：

```text
Agent 调模型 → tool_calls → 审批 → 程序执行工具
→ ToolMessage → 再调模型 → 继续或结束
```

它的作用是根据真实工具反馈修正后续行动。例如先检索某人的任职单位，再用单位名称查询相关政策，
第二次查询依赖第一次结果，无法在开始时完全确定。

**防死循环需要同时限制资源和判断进展：**

- 资源限制：最大图步数、模型调用次数、单次工具超时、任务总时限和费用预算。
- 进展判断：记录工具名、规范化参数和结果摘要；相同调用反复出现且没有新证据时停止。
- 退出处理：返回已有结论和缺口，必要时澄清；有副作用的工具还要防止重试造成重复执行。

**重新检索的触发条件**包括证据不足、多跳查询、用户改变条件及证据冲突。
应先判断缺少哪类证据，再改写查询、拆问或调整范围；资料已充分时直接回答，避免无效循环。

**项目边界**：Worker 有循环和超时限制；主图的 `GRAPH_RECURSION_LIMIT=25` 尚未传入运行配置。
120 秒是无事件等待超时，不能替代总时限；ChatRun 另有默认 900 秒运行超时配置。
主循环支持再次调用检索工具，但统一的证据充分性和重复调用检测仍待补齐。

## 5. 上下文长度怎么设计？

按模型窗口分预算，历史持久化与本轮上下文选择分开处理。

```text
系统指令 + 工具定义 + 历史 + 记忆 + 检索结果
+ 预留输出 + 安全余量 ≤ 模型窗口
```

**项目已有**：PostgreSQL Checkpoint 保存状态；多 Agent 上下文最多 12 条、约 6000 字符，
单条正文最多约 1200 字符；D2 降级按完整工具消息组裁剪，保留最新用户消息。

进一步设计时可以分层保留：

- **固定保留**：系统规则、当前目标、用户明确约束、关键数字和实体。
- **近期原文**：最近对话及完整的工具调用与返回，保证续聊和协议完整性。
- **历史摘要**：已完成步骤、关键决策、尚未解决的问题；摘要带原始记录引用。
- **外部存储**：较长工具结果和旧历史保存在数据库或文件中，需要时再检索。

按实际模型 tokenizer 计算预算；接近阈值时先去重、减少低相关证据，再压缩旧历史。
不能直接按消息条数裁剪，因为一条工具返回可能比几十条普通对话更长。
摘要也可能失真，保留原文和引用才能回查。

**边界**：100 条历史、50 万 Token 的配置尚未形成主链路硬预算，也不是模型窗口大小；
通用滚动摘要待实现。保存了历史，不等于模型本轮看到了历史。

## 6. 怎么保证格式化输出？

Schema 约束 → 解析校验 → 业务校验 → 有限重试 → 兜底。

项目 Router、Planner 使用 JSON Schema 提示词和 Pydantic，并校验目标 Agent、任务数等；
失败重试一次。支持时可进一步使用模型原生严格结构化输出。
**合法 JSON、符合 Schema、业务正确是三件事。**
例如 `target_agent` 是字符串只能说明类型正确，还要检查它是否存在、是否属于当前允许的候选。

## 7. Agent 记忆怎么设计？

短期靠 Checkpoint 保存消息与执行状态；长期保存用户事实、偏好和重要事件。

```text
对话结束 → 后台提炼 → 低置信度待确认 → 相似检索
→ 去重 / 冲突处理 → 向量化入库 → 后续按需检索
```

**写入治理**：每轮最多提炼 10 条稳定事实或事件；置信度 `<0.6` 进入待确认状态；
相似度 `≥0.92` 判重，`0.70～0.92` 交给模型判断新增、更新或合并。
更新会将旧记录标为被替代，而不是丢掉历史来源。

**读取链路**：当前问题向量化 → 按 `tenant_id + user_id + active` 过滤 →
相似度结合最近访问时间排序 → Top-5 注入上下文。这样既限制注入量，也避免跨用户串记忆。
默认 TTL 90 天，结合访问次数处理过期；发生矛盾时，当前用户陈述优先。

**“不混乱”和“不丢失”要分别处理：**

- 不混乱：隔离用户、记录来源和生效时间、识别新旧事实冲突，关键变化可人工确认。
- 不丢失：原始会话持久化，提炼失败可重试或补偿；多任务同时写记忆时需要版本或锁控制。

当前仍有缺口：相似不等于相同，“喜欢咖啡”和“不喜欢咖啡”也可能很相似；
冲突裁决失败会回退新增，部分提炼失败会跳过。不能宣称已经做到严格冲突识别和绝对不丢。

## 8. MCP、Function Calling、Skill 的区别

三者分别提供调用表达、接入协议和任务方法，可以组合使用。

| 概念 | 作用 | 项目对应 |
| --- | --- | --- |
| Function Calling | 模型生成函数名与参数 | `bind_tools`、`tool_calls` |
| MCP | 统一接入外部工具、资源和提示模板 | MCP 适配器，主要使用 Streamable HTTP |
| Skill | 封装任务步骤、知识、脚本及模板 | SkillManager、指令和资源加载 |

例如：Skill 规定处理步骤，模型生成工具调用，运行时通过 MCP 执行外部操作。

## 9. Function Calling 底层怎么执行？

LLM 生成调用请求，应用执行函数。

```text
注册工具名称、描述和参数 Schema → 传给模型
→ 模型返回工具名与参数 → 服务端校验权限、参数和审批
→ tool.ainvoke() → 带 tool_call_id 的 ToolMessage → 模型继续回答
```

函数是否执行、如何执行，以及超时、审计和幂等，都由运行时控制。

## 10. Agent 与 Workflow 的区别

Workflow 主要由程序决定路径；Agent 根据目标和执行反馈动态决定下一步。

项目的“解析 → 分块 → 向量化 → 入库”是固定流程，主 Agent 工具循环是动态决策。
选型：规则稳定、必须严格执行的业务用 Workflow；需要探索和语义判断的环节用 Agent。

## 11. 文档切分、Top-K 和 RRF

项目采用结构切分加固定窗口，在线采用混合召回与精排。

- **切分**：Markdown 一至三级标题、表格独立成块、长文本窗口兜底；默认 500 **字符**，重叠 50 字符。大表格可能超过窗口。
- **向量化**：BGE-M3，默认 1024 维，存储到 pgvector。

离线处理是“解析 → 切分 → 批量向量化 → 保存文本、向量和来源”。在线链路是：

```text
问题 → 可选 Query 改写 → BGE-M3 查询向量
→ 向量 20 条 + pg_trgm 关键词 20 条
→ RRF 去重融合并截取 20 个候选
→ BGE reranker → Top-5 证据 → 主模型生成答案
```

这是默认开启重排序时的配置；关闭重排序时会缩小召回池，重排序失败则退回粗排结果。

**切分与 Top-K 的取舍**：块太小容易丢条件和上下文，太大容易混入无关内容；
重叠能缓解边界截断，但会增加存储、索引成本及重复召回。
Top-5 是平衡覆盖、噪声和成本的初始值，应通过 Top-3/5/8/10 对比验证；
多跳问题还要检查必要证据是否全部覆盖。

```text
RRF score(d) = Σ 1 / (60 + rank_i(d))
```

RRF 按排名融合，避免直接相加不同尺度的分数；60 是融合常数，与 Top-K 无关。
同一分块在两路都排名靠前时会累加得分，按 `chunk_id` 去重。
Embedding 分别编码查询和文档；Reranker 对“查询 + 文本”联合打分，
不重新使用原来的 1024 维向量做排序。数据库召回和 RRF 不调用聊天模型。

## 12. 全链路可观测怎么实现？

一次请求对应 Trace，图节点、模型调用和工具调用对应 Span。

具体采集链路：

1. 请求开始创建 Trace，关联租户、用户、会话和请求标识。
2. 通过 `TraceContext + ContextVar` 传播上下文；跨 MQ 时放进消息信封，由 Worker 恢复。
3. 消费 LangGraph `astream_events`，用 `run_id / parent_ids` 还原节点、模型和工具的父子关系。
4. 开始事件记录时间和输入摘要；首个模型流式片段记录 TTFT；结束记录输出、usage 或异常。
5. 经异步队列或 RabbitMQ 批量落库，再聚合成本、错误率、延迟及质量评分。

例如回答慢时，先从 Trace 判断时间花在模型、检索、工具还是重试，
再看对应 Span 的输入输出摘要和错误；回答错时回查实际检索证据。
内容支持脱敏和采样，采集队列有容量与丢弃指标，避免观测阻塞主链路。

**边界**：主要覆盖应用层 Agent 链路；单次模型 TTFT 与包含排队、检索的用户首字延迟不同。

## 13. Token 成本怎么计算、怎么节省？

按所有调用累加费用，不能只算最终回答。

```text
费用 = (非缓存输入 Token × 输入单价
     + 缓存输入 Token × 缓存单价
     + 输出 Token × 输出单价) / 1,000,000
```

单价按百万 Token 计。项目支持 usage 累计和价格版本；缓存用量明细尚未完整透传，兜底价需与账单校准。

一次简单 Agentic RAG 通常是 **2 次聊天调用 + 1 次查询 Embedding + 1 次 Reranker 推理**：
第一次聊天决定检索，第二次读取工具结果生成答案，不包含路由、记忆和重试。
工具返回和历史会进入后续模型输入，因此循环次数多时，成本不仅来自新增输出。

节省成本优先减少无效调用，再控制每次输入输出：

- 简单任务直接处理；路由、提炼等任务按质量要求选模型，避免无必要的多 Agent。
- 精排后只传必要证据，历史做摘要，工具和 Skill 按需要加载。
- 限制重试及输出长度；复用适合缓存的结果，但要考虑权限和知识版本。

项目语义缓存默认关闭，通用历史摘要和完整 Skill 按需加载仍有改进空间。
本地 Embedding、Reranker 的算力成本应单独统计。

## 14. 多 Agent 如何编排、通信？何时用 A2A？

项目采用 Supervisor：

```text
Router → Planner → Worker → Aggregate → Verifier → Synthesizer
```

各阶段职责如下：

- **Router**：判断主 Agent、专用 Agent 或多 Agent 编排。
- **Planner**：生成最多 5 张 TaskCard，明确目标、必要上下文、约束、期望输出和产物引用。
- **Worker**：使用自己的模型、工具和知识库范围执行；默认单次超时 120 秒，执行失败可重试一次。
- **Verifier / Synthesizer**：检查结果，必要时重派，然后汇总成功项与缺失项。

通信以结构化任务和结果为主。LangGraph `Send` 派发并行任务，reducer 合并结果，
数据库记录任务状态；`ContextVar` 为 Worker 设置独立请求上下文，结束后恢复父上下文。
交接时保留必要事实和证据引用，避免把完整聊天历史复制给所有 Worker。

成本上，若有 n 个 Worker、各调用一次模型且无工具循环，典型编排约为
`Router 1 次 + Planner 1 次 + Worker n 次 + Synthesizer 1 次`；重试和模型校验还会增加调用。

**边界**：当前顺序分支仅依次执行，尚未自动将前任务结果写入后任务输入；
默认 Verifier 检查状态、空结果、过短结果和拒绝标记，不能保证事实正确。

**A2A** 适合跨服务、跨框架、独立部署的 Agent 交互，通过 Agent Card 发现能力、
Task 跟踪状态、Artifact 返回产物。当前项目内部用 LangGraph 协作，未接入 A2A。

## 15. 什么情况下使用多 Agent？

适合可独立并行、专长或权限不同、需要独立检查、上下文适合拆分的任务。

简单查询、强依赖步骤和频繁共享状态的任务，拆分可能增加延迟、成本和误差。
判断标准：拆分收益是否覆盖规划、通信和汇总成本。项目默认关闭多 Agent，按需启用。
例如三个独立领域的资料分析可以并行；“先查数据，再计算，再据计算结果生成报告”
应先明确依赖和结果传递，不能为了并行而同时执行。

## 16. 熔断降级策略与并发容量

项目按入口、会话、模型和 Agent 分层保护。

- **限流与排队**：API Key / IP 限流、会话约束、在线/后台独立池、有界队列。
- **端点熔断**：60 秒窗口、至少 10 个样本、错误率阈值 50%、冷却 30 秒，之后半开探测。
- **过载处理**：429 时有效并发乘 `0.8`；分级缩短输出、裁剪历史；备用模型需要配置。
- **Agent 熔断**：连续失败 3 次，默认冷却 600 秒。

这些机制解决的问题不同：限流控制进入速率，并发池限制在途调用，排队吸收短时突发，
熔断减少对故障端点的持续请求，降级降低单次请求资源消耗。
在线和后台池分开，避免记忆提炼等后台工作抢占全部交互资源。

过载降级有滞回：利用率持续高于 80% 达 60 秒进入一级降级；
进入后继续高于 90% 达 60 秒可进入二级；低于 70% 持续 120 秒后恢复，避免反复切换。

| 限制对象 | 默认上限 |
| --- | --- |
| 在线 / 后台 LLM 调用 | 200 / 8 |
| 流式入口 / 入口排队 | 240 / 50 |
| 单用户 / 单租户活跃 Run | 3 / 100 |

各限制作用范围不同，不能相加，也不等于用户并发数。

容量估算可先用 `请求吞吐 ≈ 模型槽位 / 每请求累计占用模型的秒数`。
例如每请求两次模型调用、每次占用 10 秒，200 槽位对应的理想上限约 10 请求/秒；
这只是忽略其他瓶颈的示例，不能当成项目压测结果。

**没有真实模型容量结论**。需结合 RPM/TPM、平均 Token、模型耗时、数据库和 Reranker 压测；
观察稳定吞吐、P95、错误率及队列增长，找到满足业务目标的容量。
多个保护器为进程内状态，多实例需协调额度。

## 17. RabbitMQ 的作用

用于观测异步落库、会话记忆提炼，以及可选的持久化 ChatRun 派发与恢复。

观测和记忆提炼放在后台，减少对用户回答的阻塞；不同 Worker 可以独立处理各类任务。
可靠性依靠 publisher confirm、手动 ACK、幂等消费、重试和死信。

ChatRun 使用 Transactional Outbox：

```text
同一数据库事务写 Run + Outbox
→ 发布器发送消息 → Broker 确认 → 标记已发布
→ Worker 领取任务 → 执行并持久化状态
```

数据库提交后 MQ 暂时不可用，未发布的 Outbox 可以重试；
若消息已发出但尚未标记成功时进程崩溃，也可能再次发送，因此消费者仍需幂等。
Run 另有租约、心跳和过期恢复，避免仅靠消息投递判断任务是否完成。
观测发布失败可回退本地队列，持久化 ChatRun 则依靠 Outbox 后续重试。

语义是至少一次投递，业务必须防重复；内部多 Agent 主要通过 LangGraph 通信。
MQ 和持久化 ChatRun 调度默认关闭。

## 18. 不同文档如何识别和解析？

当前按扩展名校验，上传时显式选择 `text` 或 `ocr`。

- TXT / Markdown：直接读取；PDF：`pypdf`；DOCX：`python-docx` 读取段落。
- OCR：GLM 文件解析；配置缺失或解析失败会报错，不静默切换本地解析。
- 默认上传格式：`.md,.txt,.pdf,.docx`。

待完善：自动识别扫描页、复杂版面顺序、DOCX 表格及页码坐标保留。
可先检查文件签名与 MIME，再按页提取文本、检查覆盖率与乱码情况；
文本稀少或只有图片的页走 OCR，混合型 PDF 按页选择路径。
解析后还要抽查表格、标题与阅读顺序，避免错误文本进入索引后被当成可靠知识。

## 19. Harness Engineering 是什么？

围绕模型构建可执行、可恢复、可观察、可评测的运行底座。

包含 Agent Loop、工具与权限、上下文和记忆、状态持久化、审批恢复、
重试熔断、预算、观测评测及执行环境。
项目已落地其中多项能力；统一 Token 预算和完整执行沙箱仍需补齐。

## 20. Prompt 技巧有哪些？

明确目标、边界、输入和验收标准；给出 Schema、少量典型例子和工具使用条件；
区分指令与外部资料；复杂任务分步骤；修改后用固定样本回归。

项目实例：Router 只允许候选 Agent 名；Planner 保留数字与约束；
Worker 明确职责及 `CANNOT_HANDLE`；校验失败后携带错误重试。
权限、预算和参数校验必须落在代码中。
