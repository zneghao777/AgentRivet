# 知识库索引模式与知识图谱体验升级 · 技术规格书

> 版本：v1.0.0（草案）
> 日期：2026-08-21
> 状态：待评审
> 里程碑代号：KBX
> 关联文档：
> [RAG_SPEC.md](./RAG_SPEC.md)、
> [KB_MANAGEMENT_SPEC.md](./KB_MANAGEMENT_SPEC.md)、
> [AGENTIC_RAG_UPGRADE_SPEC.md](./AGENTIC_RAG_UPGRADE_SPEC.md)、
> [GRAPH_RAG_SPEC.md](./GRAPH_RAG_SPEC.md)

本文定义知识库从“所有文档统一摄取、全局自动构图”升级为“按知识库声明
索引能力、按文档跟踪构建状态、统一路由检索”的完整方案。规格同时覆盖后端
领域模型、状态机、API、数据一致性、迁移、知识库总览、创建流程、文档导入、
图谱工作区、响应式、可访问性、测试与验收标准。

> **注意：** 本规格是现有知识库与 Graph RAG 草案的产品编排层补充。图实体、
> 关系、事件、社区的抽取与存储算法继续遵循 `GRAPH_RAG_SPEC.md`；当两份文档
> 对“是否自动构图、页面如何呈现、检索如何路由”描述不一致时，以本规格为准。

## 0. 决策摘要

本节固定实现期间不得随意重新讨论的核心产品决策，避免前端、API 和任务编排
分别产生不同语义。

1. 知识库必须区分 **标准知识库** 与 **图谱增强知识库**。
2. 图谱增强知识库必须保留标准分块、向量、关键词和 Rerank 能力，不提供
   “只有图谱、没有文本索引”的模式。
3. 文档上传默认继承知识库索引模式，不要求用户每次重新选择普通 RAG 或
   Graph RAG。
4. 图谱增强知识库可选择 **自动构建** 或 **手动构建**；默认使用自动构建。
5. 单文档是否参与图谱构建只作为高级覆盖项，默认值为 `inherit`。
6. `GRAPH_ENABLED` 仅表示部署环境是否提供图谱能力，不得再直接控制所有
   知识库自动构图。
7. 对话检索统一经过 `knowledge_search` 编排服务；标准文本召回和图谱召回
   必须在服务层融合，而不是只依赖 Agent 自行调用两个独立工具。
8. 文档解析、文本索引和图谱索引必须有独立状态，图谱失败不得使已经成功的
   标准 RAG 失效。
9. 删除、替换、重新解析和停用文档时，必须同步维护图谱证据，不得留下指向
   已删除分块的实体或关系。
10. 页面必须明确展示索引模式、构建策略、索引健康度、当前任务、失败原因和
    恢复动作。

## 1. 背景与问题

当前项目已经具备标准 RAG、混合检索、Rerank 和 Graph RAG 的主要代码路径，
但产品与数据模型仍将它们表现为同一种知识库，导致用户无法理解系统正在构建
什么、为什么需要等待，以及失败后哪部分能力仍可使用。

### 1.1 当前实现边界

当前实现存在以下已由源码确认的行为，改造必须显式处理其兼容性。

- `KnowledgeBaseCreateRequest` 只有 `name` 与 `description`，创建时无法声明
  索引模式。
- 上传接口只有 `file` 与 `replace`，没有知识库级或文档级索引策略。
- 文档解析完成后，只要 `GRAPH_ENABLED=true`，系统会自动触发图谱构建。
- `KnowledgeBase` 只有聚合的 `graph_status` 与 `graph_meta`，文档没有独立的
  图谱索引状态。
- 知识库列表和创建弹窗不展示图谱能力；所有详情页都显示知识图谱页签。
- `knowledge_search` 与 `knowledge_graph_search` 是两个独立工具，没有一个
  确定性的文本与图谱融合排序层。
- 删除或同名替换文档时，标准分块会被删除，但现有服务链路没有同步清理该
  文档的图实体、关系、事件和社区。

### 1.2 用户问题

上述实现让用户在关键操作中缺少必要的预期和控制。

- 用户不知道知识库是否会产生额外的图谱抽取成本。
- 用户无法为 FAQ、制度或短文档选择更快的标准索引。
- 用户无法判断“文档已解析”是否等同于“图谱已就绪”。
- 用户无法看出图谱失败是否影响普通问答。
- 用户无法从列表快速识别哪些知识库适合关系、多跳和全局问题。
- 用户无法知道删除或重新解析后图谱是否已经同步更新。
- Agent 可能在无图谱数据的知识库上调用图检索，得到不稳定的空结果。

### 1.3 改造目标

本次改造交付一套可理解、可治理、可恢复的统一知识库体系。

- 建立稳定的知识库索引模式和图谱构建策略。
- 建立文档级解析、文本索引、图谱索引状态机。
- 建立持久化索引任务和可观察的阶段进度。
- 建立文本与图谱的统一检索路由、融合和降级机制。
- 建立上传、替换、重解析、删除、模式切换的数据一致性规则。
- 重构知识库总览、创建流程、详情页和知识图谱工作区。
- 提供桌面、平板和窄屏下完整可用的交互体验。
- 提供可执行的迁移步骤、测试计划和验收标准。

### 1.4 非目标

以下能力不属于本次范围，后续需求不得通过隐式扩展混入 KBX 里程碑。

- 不引入 Neo4j、NebulaGraph 或其他独立图数据库。
- 不实现跨知识库图谱合并。
- 不向最终用户开放 SQL、Cypher 或任意图查询语言。
- 不提供纯 Graph、无文本分块与向量索引的知识库。
- 不让用户在上传时选择 GLM 或本地解析器；解析器仍由系统自动选择和降级。
- 不在本期实现图谱本体编辑器、Schema DSL 或复杂规则推理。
- 不在本期实现超过三跳的任意深度图遍历。
- 不以 3D 图谱、粒子动画或装饰性大屏替代数据治理界面。

## 2. 术语与产品模型

本节统一产品文案、API 枚举和代码命名。前端不得自行使用“普通库”“图库”或
“Graph 库”等含义不稳定的名称。

### 2.1 标准知识库

标准知识库提供企业文档问答的基础索引能力，适合制度、FAQ、产品手册、技术
文档和精确来源问答。

标准知识库包含以下能力：

- 文件解析与原文保存。
- 结构化分块和分块治理。
- 向量索引。
- 关键词检索。
- 混合召回、RRF 和可选 Rerank。
- 分块级来源引用和深链定位。

对应持久化枚举为：

```text
index_mode = standard
```

### 2.2 图谱增强知识库

图谱增强知识库在标准能力之上增加实体、关系、事件、社区和多跳检索，适合
人物关系、组织关系、事件脉络、跨文档关联和全局概括问题。

图谱增强知识库必须先完成标准文本索引，再运行图谱索引。图谱失败时，标准
检索仍然可用。

对应持久化枚举为：

```text
index_mode = graph_enhanced
```

### 2.3 图谱构建策略

图谱构建策略只对 `graph_enhanced` 生效，用于控制文档完成标准索引后是否立即
构建图谱。

| 枚举 | 产品文案 | 行为 |
|---|---|---|
| `auto` | 自动构建 | 文本索引成功后自动排队构建图谱 |
| `manual` | 手动构建 | 文本索引成功后标记为待构建，由用户触发 |

标准知识库的 `graph_build_policy` 必须为 `manual` 或 `null`，服务层不得触发
图任务。

### 2.4 文档级覆盖

文档级覆盖仅用于少量不适合抽取实体关系的文件，入口放在上传高级设置和文档
设置中。

| 枚举 | 产品文案 | 行为 |
|---|---|---|
| `inherit` | 跟随知识库 | 使用知识库的索引模式与构建策略 |
| `include` | 参与图谱 | 在图谱增强知识库中强制参与图谱构建 |
| `exclude` | 不参与图谱 | 仅构建标准文本索引 |

标准知识库收到 `include` 时必须返回 `409 INDEX_MODE_CONFLICT`，不得静默升级。

### 2.5 检索模式

检索模式描述查询阶段如何使用已经就绪的索引，不等同于知识库索引模式。

| 枚举 | 产品文案 | 行为 |
|---|---|---|
| `auto` | 自动 | 根据问题和索引就绪度选择文本或融合检索 |
| `text` | 文本检索 | 只使用向量、关键词和 Rerank |
| `graph` | 图谱检索 | 只返回实体、关系、社区、事件和证据 |
| `fused` | 融合检索 | 并行运行文本与图谱通道并融合结果 |

对话默认使用 `auto`。测试检索页面允许用户显式切换，用于比较和评测。

## 3. 领域模型与数据库变更

数据模型必须区分“知识库声明的能力”“文档当前处理状态”和“后台任务执行
记录”。只在知识库上存一个 `graph_status` 无法表达部分成功和可恢复失败。

### 3.1 `KnowledgeBase` 扩展

在现有 `knowledge_bases` 表上增加以下字段，并保留已有统计字段。

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `index_mode` | `VARCHAR(24)` | `standard` | `standard` 或 `graph_enhanced` |
| `graph_build_policy` | `VARCHAR(16)` | `manual` | `auto` 或 `manual` |
| `index_status` | `VARCHAR(16)` | `empty` | 知识库聚合索引健康状态 |
| `graph_status` | `VARCHAR(16)` | `disabled` | 图谱聚合状态 |
| `graph_version` | `INTEGER` | `1` | 图谱构建算法或配置版本 |
| `graph_meta` | `JSONB` | `{}` | 图谱计数、时间和最近错误摘要 |
| `settings` | `JSONB` | `{}` | 可扩展的索引配置，不存运行状态 |

数据库必须增加约束：

```sql
CHECK (index_mode IN ('standard', 'graph_enhanced'))
CHECK (graph_build_policy IN ('auto', 'manual'))
CHECK (
  index_mode = 'graph_enhanced'
  OR graph_build_policy = 'manual'
)
```

`settings` 第一阶段允许保存以下可选项：

```json
{
  "chunk_size": 500,
  "chunk_overlap": 80,
  "graph_max_hop": 3,
  "graph_entity_types": ["person", "organization", "place", "event"]
}
```

### 3.2 `DocumentMeta` 扩展

文档记录必须独立表达解析、文本索引与图谱索引状态，以支持页面阶段进度和
局部重试。

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `graph_override` | `VARCHAR(16)` | `inherit` | 文档级图谱覆盖策略 |
| `vector_status` | `VARCHAR(16)` | `pending` | 文本分块与向量索引状态 |
| `graph_status` | `VARCHAR(16)` | `excluded` | 文档图谱索引状态 |
| `vector_error` | `TEXT` | `null` | 文本索引最近错误 |
| `graph_error` | `TEXT` | `null` | 图谱索引最近错误 |
| `vector_indexed_at` | `TIMESTAMPTZ` | `null` | 文本索引完成时间 |
| `graph_indexed_at` | `TIMESTAMPTZ` | `null` | 图谱索引完成时间 |
| `graph_version` | `INTEGER` | `null` | 文档当前图谱版本 |
| `content_hash` | `VARCHAR(64)` | `null` | 幂等与脏数据判断 |

`parse_status` 继续只描述原文解析，不得复用为文本或图谱索引状态。

### 3.3 `KnowledgeIndexJob` 新表

后台解析和索引任务必须持久化。进程内 `asyncio.Task` 可作为执行器，但不能是
任务状态的唯一来源。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `UUID PK` | 任务 ID |
| `tenant_id` | `VARCHAR(64)` | 租户隔离 |
| `kb_id` | `UUID` | 知识库 ID |
| `doc_id` | `BIGINT NULL` | 文档 ID；全库任务为空 |
| `job_type` | `VARCHAR(24)` | `parse`、`vectorize`、`graph_build`、`graph_cleanup` |
| `status` | `VARCHAR(16)` | `queued`、`running`、`succeeded`、`failed`、`cancelled` |
| `stage` | `VARCHAR(32)` | 当前细分阶段 |
| `progress` | `INTEGER` | 0 到 100，仅表示已知工作量 |
| `attempt` | `INTEGER` | 当前尝试次数 |
| `max_attempts` | `INTEGER` | 最大尝试次数 |
| `error_code` | `VARCHAR(64) NULL` | 稳定错误码 |
| `error_message` | `TEXT NULL` | 用户可读错误摘要 |
| `meta` | `JSONB` | chunk 数、批次数、token 数等 |
| `started_at` | `TIMESTAMPTZ NULL` | 首次开始时间 |
| `finished_at` | `TIMESTAMPTZ NULL` | 最终结束时间 |
| `created_at` | `TIMESTAMPTZ` | 创建时间 |
| `updated_at` | `TIMESTAMPTZ` | 更新时间 |

同一文档同一类型只能有一个 `queued` 或 `running` 任务。服务层必须通过数据库
唯一约束或带锁查询避免重复构建。

### 3.4 状态枚举

状态必须使用稳定枚举，前端只负责映射文案和色彩，不得通过错误字符串猜测
业务状态。

知识库 `index_status` 使用：

```text
empty | indexing | ready | partial | failed | stale
```

知识库 `graph_status` 使用：

```text
disabled | none | pending | building | ready | partial | failed | stale
```

文档 `vector_status` 使用：

```text
pending | building | ready | failed | stale
```

文档 `graph_status` 使用：

```text
excluded | pending | building | ready | failed | stale
```

### 3.5 聚合状态规则

知识库聚合状态必须由文档状态计算，不能只由最后一个完成的后台任务直接覆盖。

`graph_status` 的计算顺序如下：

1. 当 `index_mode=standard` 时，返回 `disabled`。
2. 当没有参与图谱的文档时，返回 `none`。
3. 当任一参与文档为 `building` 时，返回 `building`。
4. 当任一参与文档为 `pending` 且没有构建中任务时，返回 `pending`。
5. 当全部参与文档为 `ready` 时，返回 `ready`。
6. 当存在 `ready`，同时存在 `failed` 或 `stale` 时，返回 `partial`。
7. 当全部参与文档都失败时，返回 `failed`。
8. 当没有失败但存在过期索引时，返回 `stale`。

聚合逻辑必须集中在服务层纯函数中，并以单元测试覆盖所有组合。

## 4. 状态机与核心流程

本节规定用户动作与后台任务的完整时序。任何入口都必须复用同一编排服务，
避免上传、重新解析和批量重建产生不同的数据一致性语义。

### 4.1 创建标准知识库

标准知识库创建后不运行任何索引任务，初始状态如下：

```text
index_mode = standard
index_status = empty
graph_build_policy = manual
graph_status = disabled
```

用户上传文档后执行：

```text
上传
  → 安全校验与落盘
  → 解析原文
  → 分块
  → 向量化与关键词索引
  → 文本索引 ready
  → 文档可检索
```

### 4.2 创建图谱增强知识库

图谱增强知识库创建后也不立即构图，因为它还没有文档。初始状态如下：

```text
index_mode = graph_enhanced
index_status = empty
graph_build_policy = auto | manual
graph_status = none
```

### 4.3 自动构建图谱的文档上传

当知识库为图谱增强模式且策略为 `auto` 时，文档先完成标准文本索引，再排队
运行图谱任务。

```text
上传
  → 解析
  → 分块
  → 向量化
  → 文本索引 ready，可立即用于标准问答
  → 图谱任务 queued
  → 实体 / 关系 / 事件抽取
  → 实体归一化
  → 社区计算与摘要
  → 图谱索引 ready，可用于融合问答
```

图谱构建失败时必须保留 `vector_status=ready`，页面显示“文本检索可用，图谱
构建失败”，并提供仅重试图谱的操作。

### 4.4 手动构建图谱的文档上传

当策略为 `manual` 时，文本索引完成后将文档 `graph_status` 设置为 `pending`，
不得自动创建 `graph_build` 任务。

页面在文档行和图谱页显示 **待构建**，用户可执行：

- **构建待处理文档**：只处理所有 `pending` 文档。
- **构建此文档**：只处理当前文档。
- **全量重建**：清理当前知识库图数据后处理所有参与文档。

### 4.5 单文档排除

当 `graph_override=exclude` 时，文档完成文本索引后将 `graph_status` 设置为
`excluded`，不得进入图任务。

用户将排除改为参与时，系统必须执行以下动作：

1. 校验知识库是图谱增强模式。
2. 将文档状态设置为 `pending`。
3. 当策略为 `auto` 时立即创建图谱任务。
4. 当策略为 `manual` 时等待用户触发。

### 4.6 重新解析

重新解析会改变分块和证据锚点，必须把文本和图谱同时视为过期。

```text
用户确认重新解析
  → 标记 vector_status=stale
  → 标记 graph_status=stale 或 excluded
  → 删除旧图谱证据和该文档产生的图数据
  → 删除旧分块
  → 重新解析与文本索引
  → 按当前图谱策略重新构建或进入 pending
```

清理图谱与删除旧分块必须在可恢复事务边界内执行。清理失败时不得继续写入
新图谱，以免同一文档出现两个版本的事实。

### 4.7 同名替换

同名替换等价于“删除旧版本并创建新版本”，但必须在 UI 中明确提示旧引用和
图谱证据将更新。

服务层必须按以下顺序执行：

1. 保存新文件并完成格式校验。
2. 创建替换任务和新文档版本记录。
3. 清理旧文档图数据与标准分块。
4. 切换到新文档记录。
5. 运行新的解析与索引流水线。
6. 失败时保留可诊断状态，不得无记录地丢失旧文件。

第一阶段若暂不实现文档版本表，至少必须保证图谱清理在删除旧
`DocumentMeta` 前完成。

### 4.8 删除文档

删除是破坏性操作，用户必须确认删除范围。确认文案必须说明将删除原文件、
分块、向量、实体、关系、事件、社区归属和历史引用目标。

删除顺序如下：

```text
阻止新的文档任务
  → 取消 queued 任务
  → 等待或标记 running 任务取消
  → 删除该文档的关系与事件
  → 删除仅由该文档支持的实体
  → 更新跨文档实体的 chunk_ids 与 doc_id
  → 重算受影响社区
  → 删除分块、文件和 DocumentMeta
  → 刷新知识库聚合状态与计数
```

### 4.9 知识库模式切换

模式切换属于重索引操作，不得作为普通表单字段直接保存。

从 `standard` 切换为 `graph_enhanced` 时：

- 用户选择自动或手动构建策略。
- 页面显示参与文档数和预计处理 chunk 数。
- 自动策略在确认后为历史文档创建图谱任务。
- 手动策略将历史文档标记为 `pending`。
- 文本索引和原有引用不受影响。

从 `graph_enhanced` 切换为 `standard` 时：

- 停止创建新的图任务。
- 取消尚未开始的图任务。
- 默认保留图谱数据但禁用图检索，便于恢复。
- 用户可另行执行 **删除图谱数据**。
- 删除图谱数据必须二次确认，且不得删除标准分块。

### 4.10 平台图谱能力关闭

当部署环境设置 `GRAPH_ENABLED=false` 时，平台不提供图谱构建与检索，但不得
篡改数据库中原有的 `index_mode`。

前端必须表现为：

- 已有图谱增强库显示 **图谱服务不可用**，而不是伪装成标准库。
- 创建弹窗禁用图谱增强选项，并显示管理员配置说明。
- 文本检索继续可用。
- 图谱构建按钮禁用，保留状态和历史数据查看入口。

## 5. 统一检索与 Agent 接入

知识库类型只有在查询阶段真正限制和路由检索能力，才算形成完整边界。本次
必须从“两个工具由模型碰运气调用”升级为“一个统一入口按数据状态确定执行”。

### 5.1 统一服务入口

服务层新增统一入口，供 API、测试检索和 Agent 工具复用。

```python
async def retrieve_knowledge(
    db: AsyncSession,
    *,
    tenant_id: str,
    query: str,
    kb_ids: list[UUID] | None,
    mode: str = "auto",
    top_k: int = 5,
    rerank: bool = True,
    expand_query: bool = False,
) -> UnifiedKnowledgeResult:
    ...
```

`UnifiedKnowledgeResult` 必须包含：

```text
query
resolved_mode
text_hits[]
graph_context.entities[]
graph_context.relations[]
graph_context.communities[]
graph_context.events[]
evidence_chunks[]
citations[]
degradations[]
timings
```

### 5.2 `auto` 路由规则

`auto` 必须是可测试的规则与索引就绪度组合，不能只依赖 LLM 任意选择工具。

1. 解析知识库白名单并过滤当前租户不可见或停用的知识库。
2. 将标准知识库加入文本通道。
3. 将图谱增强且 `graph_status in ('ready', 'partial')` 的知识库加入图通道。
4. 对实体关系、多跳、时间线、全局概括类问题运行融合检索。
5. 对精确文档、制度、型号、编号和来源定位问题优先运行文本检索。
6. 分类不确定时运行文本检索，并在预算允许时并行运行图检索。
7. 图通道失败或超时时返回文本结果，同时记录降级原因。

问题分类第一阶段可使用规则与轻量 LLM 分类，但分类失败必须回退到文本检索。

### 5.3 融合流程

融合模式按以下顺序执行：

```text
用户问题
  ├─ 文本通道：query expand → vector + keyword → RRF → candidates
  └─ 图谱通道：entity recall → graph expansion / community / timeline
                           ↓
             graph evidence chunk_ids 回查原始分块
                           ↓
              按 chunk_id 去重并合并通道特征
                           ↓
                     可选 Rerank
                           ↓
             统一来源引用 + 结构化图谱上下文
```

文本通道与图谱通道不得分别生成互相冲突的最终答案。它们只提供候选证据和结构
上下文，最终由同一次回答生成使用。

### 5.4 工具兼容策略

`knowledge_search` 升级为唯一推荐给 Agent 的知识入口，参数增加：

```text
mode = auto | text | graph | fused
```

`knowledge_graph_search` 第一阶段保留，供显式图查询、管理页调试和向后兼容，
但不再作为默认工具注册给所有 Agent。后续确认无调用方后再弃用。

### 5.5 降级规则

检索必须优先保证可回答性和来源可信度。

| 条件 | 行为 | 用户可见提示 |
|---|---|---|
| 图谱未构建 | 回退文本检索 | “图谱尚未就绪，本次使用文本检索” |
| 图谱部分失败 | 使用就绪图数据并融合文本 | “部分文档图谱不可用” |
| 图谱超时 | 返回文本结果 | 调试面板记录超时，普通对话不弹阻断错误 |
| Rerank 不可用 | 返回融合粗排 | 记录 `rerank_skipped` |
| 文本索引失败但图谱存在 | 仅管理页允许图调试 | 对话不将无可追溯图结果作为充分证据 |

### 5.6 来源与溯源

融合结果的每条事实必须尽量关联原始 `chunk_id`。图关系和事件没有有效证据
分块时，可以作为辅助上下文，但不得渲染成可验证引用。

统一引用结构如下：

```json
{
  "kb_id": "uuid",
  "doc_id": 42,
  "chunk_id": 108,
  "source_file": "组织架构说明.pdf",
  "channels": ["text", "graph"],
  "score": 0.91,
  "graph_paths": ["张三-任职于-产品部"]
}
```

## 6. API 设计

API 必须保持旧调用兼容，同时把索引模式、状态和任务作为一等资源暴露给前端。
所有接口继续执行租户过滤，越权资源返回 404。

### 6.1 创建知识库

`POST /api/v1/knowledge-bases`

请求：

```json
{
  "name": "组织与人员知识库",
  "description": "组织架构、岗位和人员关系",
  "index_mode": "graph_enhanced",
  "graph_build_policy": "auto"
}
```

兼容规则：旧客户端未传 `index_mode` 时创建 `standard`，未传
`graph_build_policy` 时使用 `manual`。

响应必须增加：

```json
{
  "kb_id": "uuid",
  "name": "组织与人员知识库",
  "description": "组织架构、岗位和人员关系",
  "index_mode": "graph_enhanced",
  "graph_build_policy": "auto",
  "index_status": "empty",
  "graph_status": "none",
  "doc_count": 0,
  "chunk_count": 0,
  "entity_count": 0,
  "active_job_count": 0,
  "status": "active"
}
```

### 6.2 更新索引设置

`PATCH /api/v1/knowledge-bases/{kb_id}/index-settings`

该接口只更新不会触发模式迁移的设置，例如自动或手动构建策略。`index_mode`
不得通过本接口修改。

```json
{
  "graph_build_policy": "manual",
  "settings": {
    "graph_max_hop": 3
  }
}
```

### 6.3 切换索引模式

`POST /api/v1/knowledge-bases/{kb_id}/index-mode-transition`

请求：

```json
{
  "target_mode": "graph_enhanced",
  "graph_build_policy": "auto",
  "build_existing_documents": true
}
```

响应返回转换任务、受影响文档和预估工作量：

```json
{
  "transition_id": "uuid",
  "affected_documents": 12,
  "estimated_chunks": 1840,
  "job_ids": ["uuid"]
}
```

### 6.4 上传文档

`POST /api/v1/knowledge-bases/{kb_id}/documents/upload`

Multipart 字段：

```text
file: binary
replace: true | false
graph_override: inherit | include | exclude
```

`graph_override` 可省略，默认 `inherit`。响应必须包含三个阶段状态和任务 ID。

```json
{
  "kb_id": "uuid",
  "doc_id": 42,
  "source_file": "组织架构说明.pdf",
  "parse_status": "pending",
  "vector_status": "pending",
  "graph_status": "pending",
  "job_ids": ["uuid"]
}
```

### 6.5 文档状态与任务

前端轮询优先使用轻量任务接口，避免反复拉取完整知识库详情。

| Method | Path | 说明 |
|---|---|---|
| `GET` | `/knowledge-bases/{kb_id}/jobs?status=active` | 当前活动任务 |
| `GET` | `/knowledge-bases/{kb_id}/documents/{doc_id}/index-status` | 单文档阶段状态 |
| `POST` | `/knowledge-bases/{kb_id}/documents/{doc_id}/retry` | 按失败阶段重试 |
| `POST` | `/knowledge-bases/{kb_id}/documents/{doc_id}/graph/build` | 构建单文档图谱 |
| `PATCH` | `/knowledge-bases/{kb_id}/documents/{doc_id}/graph-override` | 修改覆盖策略 |
| `POST` | `/knowledge-bases/{kb_id}/jobs/{job_id}/cancel` | 取消可取消任务 |

轮询建议采用 2 秒、3 秒、5 秒渐进间隔；页面隐藏后停止轮询，重新获得焦点时
立即刷新。后续可升级为 SSE，但不是本期硬依赖。

### 6.6 图谱管理 API 归一

现有 `/api/v1/kbs/{kb_id}/graph/*` 必须保留兼容路由，同时新增与知识库 API
一致的正式路径。

| Method | 正式路径 | 说明 |
|---|---|---|
| `GET` | `/knowledge-bases/{kb_id}/graph/status` | 图谱聚合状态与计数 |
| `POST` | `/knowledge-bases/{kb_id}/graph/build-pending` | 构建所有待处理文档 |
| `POST` | `/knowledge-bases/{kb_id}/graph/rebuild` | 全量重建 |
| `DELETE` | `/knowledge-bases/{kb_id}/graph` | 删除图谱数据 |
| `GET` | `/knowledge-bases/{kb_id}/graph/entities` | 实体分页与过滤 |
| `GET` | `/knowledge-bases/{kb_id}/graph/subgraph` | 获取受限规模子图 |
| `POST` | `/knowledge-bases/{kb_id}/graph/search` | 图谱语义检索 |
| `GET` | `/knowledge-bases/{kb_id}/graph/entities/{id}` | 实体详情与邻居 |

`subgraph` 必须支持 `entity_id`、`hop`、`types` 和 `limit`，单次默认最多返回
100 个节点和 200 条边，硬上限分别为 300 和 600。

### 6.7 统一测试检索 API

`POST /api/v1/knowledge-bases/{kb_id}/test-search`

请求增加 `mode`：

```json
{
  "query": "张三与产品部是什么关系？",
  "mode": "fused",
  "top_k": 5,
  "rerank": true,
  "expand_query": false,
  "graph_hop": 2
}
```

响应必须同时返回文本结果、图谱上下文、解析后的实际模式、降级原因和各阶段
耗时，供页面对比而不依赖解析工具 Markdown。

### 6.8 错误码

接口必须返回稳定错误码，前端按错误码提供恢复动作。

| 错误码 | HTTP | 含义 | 恢复动作 |
|---|---:|---|---|
| `GRAPH_PLATFORM_DISABLED` | 503 | 部署未开启图谱能力 | 联系管理员或使用标准模式 |
| `INDEX_MODE_CONFLICT` | 409 | 操作与知识库模式冲突 | 切换模式或修改覆盖项 |
| `INDEX_JOB_ALREADY_RUNNING` | 409 | 同类任务正在执行 | 查看现有任务 |
| `GRAPH_NOT_READY` | 409 | 图谱尚未可查询 | 构建图谱或使用文本检索 |
| `DOCUMENT_INDEX_STALE` | 409 | 文档索引已过期 | 重新索引 |
| `INDEX_JOB_FAILED` | 422 | 后台任务失败 | 查看阶段错误并重试 |
| `DESTRUCTIVE_CONFIRMATION_REQUIRED` | 409 | 缺少破坏性确认 | 重新确认删除范围 |

## 7. 后端编排与数据一致性

后端必须把状态变更、任务创建和数据清理放入明确的服务边界，不能继续由路由、
`ingest.py` 和图谱模块分别修改状态。

### 7.1 组件职责

建议形成以下服务分层：

```text
KnowledgeService
  ├── KnowledgePolicyService      模式、策略与权限判断
  ├── DocumentIngestService       文件、解析、分块与向量编排
  ├── IndexJobService             任务持久化、去重、重试与取消
  ├── GraphIndexService           图谱构建、增量更新与清理
  ├── KnowledgeRetrievalService   文本/图谱路由与融合
  └── KnowledgeStatusService      文档和知识库聚合状态
```

路由只负责校验请求、调用服务和转换响应，不得直接创建后台任务或修改图表。

### 7.2 策略判断函数

是否构图必须由一个纯函数决定，并覆盖所有组合。

```python
def resolve_graph_action(
    *,
    platform_enabled: bool,
    index_mode: str,
    build_policy: str,
    graph_override: str,
) -> Literal["excluded", "pending", "enqueue"]:
    ...
```

`ingest.py` 不得直接读取 `GRAPH_ENABLED` 后无条件触发图谱任务。

### 7.3 幂等规则

每次图谱构建必须绑定：

```text
tenant_id + kb_id + doc_id + content_hash + graph_version
```

当五个值与最后成功任务一致时，重复请求直接返回已有结果。内容哈希或
`graph_version` 变化时，将旧索引标记为 `stale` 并创建新任务。

### 7.4 增量删除规则

删除某文档图数据时必须区分文档独占事实和跨文档共享事实。

- 关系和事件按 `doc_id` 或证据 `chunk_id` 删除。
- 实体移除该文档的 `chunk_ids`。
- 实体仍有其他文档证据时保留。
- 实体失去全部证据时删除，并级联清理关系。
- 社区必须对受影响连通分量重新计算，不得仅删除社区成员 ID。

### 7.5 并发控制

同一知识库最多允许一个全量重建任务。同一文档最多允许一个图谱构建任务。
不同文档允许在 `GRAPH_CONCURRENCY` 范围内并行，但实体归一化和社区更新必须
使用知识库级锁或串行提交，避免重复实体和丢失更新。

### 7.6 任务恢复

应用启动时必须扫描超时的 `queued` 和 `running` 任务。

- `queued` 任务重新入队。
- 超过心跳阈值的 `running` 任务标记为可重试失败。
- 未超过 `max_attempts` 的任务自动重试。
- 超过最大尝试次数的任务保持失败，等待人工操作。

如果本期仍使用进程内执行器，持久化任务恢复必须作为上线前硬性验收项。

## 8. UI 设计系统

知识库页面定位为明亮、专业、数据优先的企业知识工作台。视觉必须克制，信息
密度高于营销页面，同时保持清晰的层级、状态反馈和操作安全感。

### 8.1 视觉方向

页面延续当前项目 CSS 变量和 Material Symbols 图标体系，不引入独立主题。

- 使用白色或浅灰页面背景和清晰的实体表面。
- 使用品牌蓝作为主要操作和选中态，不使用大面积渐变。
- 使用细边框、弱阴影和 10 至 14 像素圆角。
- 以表格、状态条、指标带和检视器承载信息。
- 避免玻璃拟态、霓虹、巨型阴影、装饰性光晕和卡片套卡片。
- 标题字体沿用项目字体，不因本功能额外引入 Web Font。
- 代码、ID、哈希和任务号使用项目等宽字体。

### 8.2 颜色语义

颜色必须与文字和图标组合使用，不得只靠颜色表达状态。

| 语义 | 建议色 | 用途 |
|---|---|---|
| 品牌/主要操作 | 项目 `brand-600` | 主要按钮、选中态、焦点 |
| 成功/就绪 | 绿色 | 已解析、已索引、图谱就绪 |
| 处理中 | 蓝色 | 排队、解析中、构建中 |
| 待处理/部分可用 | 琥珀色 | 待构建、部分失败、索引过期 |
| 失败/破坏性 | 红色 | 失败、删除、不可恢复操作 |
| 不参与/停用 | 中性灰 | 标准库图谱、排除文档、停用状态 |

普通文本对背景的对比度必须达到 4.5:1。浅色模式的说明文字不得使用低于
项目 `gray-600` 的对比度。

### 8.3 间距与密度

页面使用统一的 4 像素间距基线。

- 页面左右内边距：桌面 24 像素，平板 20 像素，窄屏 16 像素。
- 主区块间距：24 像素。
- 区块内部间距：16 像素。
- 紧凑表格行高：48 至 52 像素。
- 主要按钮最小高度：40 像素。
- 触控目标最小尺寸：44 × 44 像素。
- 正文行高：1.5 至 1.7。

### 8.4 状态组件

全站统一使用以下知识库状态组件，禁止每个页面重新拼接文案和颜色。

- `KnowledgeModeBadge`：标准、图谱增强。
- `IndexHealthBadge`：空、索引中、就绪、部分可用、失败、已过期。
- `PipelineStatus`：解析、文本索引、图谱索引三阶段。
- `JobProgress`：任务类型、阶段、进度、耗时和取消入口。
- `CapabilityNotice`：平台能力关闭或功能降级说明。

### 8.5 动效

动效只用于状态变化和空间关系，不承担装饰作用。

- Hover、focus 和展开过渡使用 150 至 220 毫秒。
- 使用 `opacity` 和 `transform`，避免动画修改宽高导致布局跳动。
- 新任务出现时允许一次淡入，不循环闪烁。
- 进度未知时使用低干扰 spinner；进度可知时使用进度条。
- `prefers-reduced-motion: reduce` 下关闭平滑滚动、脉冲和拓扑过渡。

## 10. 知识库总览页面

总览页必须帮助用户在十秒内回答三个问题：有哪些知识库、每个库具备什么能力、
哪些库需要处理。

### 10.1 页面头部

页面头部包含标题、说明、**新建知识库** 和 **刷新**。说明文案改为：

> 管理标准检索与知识图谱，让 Agent 基于可追溯的企业知识回答。

### 10.2 指标带

指标带建议展示四项，不使用大卡片嵌套。

| 指标 | 主值 | 辅助信息 |
|---|---:|---|
| 知识库 | 总数 | 已启用数量 |
| 图谱增强 | 图谱增强库数量 | 已就绪数量 |
| 文档 | 文档总数 | 当前处理中数量 |
| 需处理 | 失败与过期总数 | 点击后应用过滤 |

指标 **需处理** 可点击，点击后设置健康度过滤为“部分可用、失败、已过期”。

### 10.3 筛选工具栏

工具栏包含以下控件：

- 搜索：名称、描述和 ID，输入使用 250 毫秒防抖。
- 类型：全部、标准、图谱增强。
- 健康度：全部、就绪、处理中、部分可用、失败、已过期。
- 状态：全部、已启用、已停用。
- 排序：最近更新、名称、文档数、问题优先。

筛选状态写入 URL 查询参数，刷新和返回时保持。

### 10.4 数据列表

桌面端使用单层数据列表，列定义如下：

| 列 | 内容 |
|---|---|
| 知识库 | 图标、名称、描述和模式徽标 |
| 索引健康 | 聚合状态、失败或待处理数量 |
| 文档 | 文档数 |
| 分块/实体 | 标准库显示分块；图谱增强库同时显示实体数 |
| 活动任务 | 任务数或最近任务阶段 |
| 最后更新 | 相对时间，Tooltip 显示绝对时间 |

单击行选中并打开右侧检视器；双击或按 Enter 进入详情。行 Hover 不使用缩放，
只调整背景、边框或阴影，避免表格跳动。

### 10.5 右侧检视器

检视器按以下顺序呈现信息：

1. 名称、模式、启用状态和健康状态。
2. 描述与知识库 ID。
3. 文档、分块、实体、关系和活动任务计数。
4. 当前问题摘要，例如“2 个文档图谱构建失败”。
5. **上传文档**、**进入详情** 和 **删除知识库**。

当知识库存在失败任务时，主操作改为 **查看并处理**，不得只显示一个红色状态。

### 10.6 空态、加载与错误

页面必须覆盖以下状态：

- 首次加载使用保持表头宽度的骨架行，避免内容跳动。
- 没有知识库时显示模式说明和 **新建知识库**。
- 筛选无结果时显示 **清除筛选**，不显示创建引导。
- 请求失败时在列表区域显示错误摘要、请求 ID 和 **重新加载**。

## 11. 新建知识库流程

创建流程必须在提交前让用户理解索引能力和成本差异。推荐使用宽 720 像素的
两步 Modal；窄屏使用全屏 Sheet。

### 11.1 第一步：基本信息

第一步包含以下字段：

- **名称**：必填，1 至 128 字符，失焦时检查同名。
- **描述**：可选，建议说明知识范围和预期问题。

校验错误显示在字段下方。名称输入框必须有可见标签，不能只依赖 placeholder。

### 11.2 第二步：索引模式

第二步使用两个并列的单选模式卡片，而不是普通下拉框。

**标准知识库** 卡片包含：

- 图标：`description` 或 `manage_search`。
- 一句话：快速构建可追溯的文档检索。
- 能力：向量、关键词、Rerank、来源引用。
- 适用：制度、FAQ、手册、技术文档。
- 标签：构建快、成本低。

**图谱增强知识库** 卡片包含：

- 图标：`account_tree`。
- 一句话：在标准检索上增加实体关系和多跳推理。
- 能力：标准能力、实体、关系、事件、社区。
- 适用：组织、人物、事件脉络、跨文档关联。
- 标签：构建较慢、产生额外模型调用。

选择图谱增强后展开 **图谱构建方式**：

```text
● 文档索引完成后自动构建（推荐）
○ 由我手动触发构建
```

### 11.3 创建摘要

Modal 底部在最终提交前显示一行摘要：

> 将创建“组织与人员知识库”，使用图谱增强索引，上传后自动构建图谱。

提交期间禁用返回、关闭和重复提交。成功后进入新知识库详情的文档页，并显示
上传引导；失败时保留表单值。

### 11.4 平台能力不可用

当 `GRAPH_ENABLED=false` 时，图谱增强卡片保持可见但禁用，附带：

> 当前环境未启用图谱服务。你仍可创建标准知识库。

不得直接隐藏图谱选项，否则用户无法理解不同环境的能力差异。

## 12. 知识库详情页面

详情页必须从“多个功能页签集合”升级为围绕索引健康和知识治理的工作台。

### 12.1 页面头部

头部左侧显示面包屑、名称、描述和模式徽标。右侧显示聚合健康状态、最后更新
时间、**上传文档** 和更多操作菜单。

当存在活动任务时，头部显示紧凑任务提示：

> 正在处理 2 个文档 · 当前阶段：图谱抽取 38%

点击提示跳转到概览的任务区。

### 12.2 概览页签

概览页使用单层区块组织，不使用卡片套卡片。

第一行显示：

- 文档数。
- 可检索分块数。
- 图谱实体与关系数，仅图谱增强库显示。
- 最近 24 小时失败任务数。

第二部分显示 **索引流水线健康**：

```text
文档解析       12/12 就绪
文本索引       12/12 就绪
知识图谱       10/12 就绪 · 1 待构建 · 1 失败
```

第三部分显示活动任务与最近失败。失败项必须提供 **查看错误** 和 **重试失败阶段**。

第四部分显示最近文档和最近检索评测结果。

### 12.3 页签可见性

页签遵循以下规则：

- 标准知识库不显示 **知识图谱**。
- 图谱增强知识库始终显示 **知识图谱**，即使平台服务临时不可用。
- 存在深链参数时，优先打开对应页签。
- 窄屏将侧边导航变成顶部可横向滚动的 Tabs。

## 13. 文档上传与文档管理

上传体验必须提前解释处理流水线，并让用户清楚地区分“文件已上传”“文本已可
检索”和“图谱已就绪”。

### 13.1 上传入口

总览检视器、详情头部和文档页都可打开同一个上传 Modal。不得维护三套不同的
上传实现。

### 13.2 上传 Modal

Modal 包含以下区域：

1. 拖放区和 **选择文件**。
2. 支持格式、单文件大小和批量数量说明。
3. 待上传文件列表，显示文件名、大小、重复文件提示和移除操作。
4. 即将执行的流水线预览。
5. 折叠的 **高级设置**。

标准知识库的流水线预览：

```text
解析文档 → 生成分块 → 建立文本索引
```

图谱增强知识库的流水线预览：

```text
解析文档 → 生成分块 → 建立文本索引 → 构建知识图谱
```

### 13.3 高级设置

高级设置只在图谱增强库显示，字段为：

```text
图谱参与方式
● 跟随知识库设置
○ 参与图谱构建
○ 不参与图谱构建
```

当知识库是手动构建策略时，说明文案必须写明：

> 上传完成后文本检索立即可用，图谱将保持待构建，直到你手动触发。

### 13.4 上传进度

文件传输进度与后台索引进度必须分开显示。

- 文件传输阶段显示字节进度。
- 上传完成后关闭传输进度，创建文档任务行。
- 后台任务在文档列表中继续更新，不强制用户保持 Modal 打开。
- 用户关闭 Modal 后通过全局消息告知“上传完成，后台正在建立索引”。

### 13.5 文档列表

文档列表桌面端采用以下列：

| 列 | 内容 |
|---|---|
| 文档 | 文件图标、文件名、大小 |
| 解析 | 状态与解析来源 |
| 文本索引 | 状态、分块数 |
| 图谱索引 | 状态、实体数或排除原因 |
| 更新时间 | 相对时间 |
| 操作 | 预览、重试、更多 |

标准知识库隐藏图谱索引列。图谱增强库必须显示该列，不能只在图谱页展示失败。

### 13.6 三阶段状态

每行使用紧凑 `PipelineStatus`，状态文案如下：

```text
解析：等待 / 解析中 / 已完成 / 失败
文本：等待 / 建立中 / 可检索 / 失败 / 已过期
图谱：不参与 / 待构建 / 构建中 / 已就绪 / 失败 / 已过期
```

处理中状态显示具体阶段，例如“抽取关系 3/8 批”，不要始终显示模糊的“处理中”。

### 13.7 文档检视器

单击文档行打开右侧检视器，依次显示：

- 文件信息和内容哈希摘要。
- 三阶段状态与完成时间。
- 分块、实体、关系和事件计数。
- 最近任务和错误详情。
- 图谱参与方式。
- **查看分块**、**构建图谱**、**重试失败阶段**、**重新解析** 和 **删除**。

操作根据状态动态显示，不提供当前状态下无意义的按钮。

### 13.8 失败恢复

错误信息必须包含阶段、简短原因、发生时间、请求 ID 和推荐动作。

示例：

> 图谱构建失败：抽取模型在 30 秒内未响应。文本检索仍可使用。你可以重试
> 图谱构建，或将本文档设为不参与图谱。

重试按钮必须只重试失败阶段，除非用户明确选择重新解析。

## 14. 知识图谱工作区

知识图谱页不能只展示实体卡片和关系文本。它必须同时支持探索、验证、治理和
检索，并保证大图下的性能与可访问性。

### 14.1 页面结构

桌面端采用三段结构：

```text
状态与操作栏
查询与过滤栏
拓扑画布 / 数据表主区 + 右侧实体检视器
```

页面顶部不重复包裹多层卡片；主画布和数据表共享一个带边框的数据表面。

### 14.2 状态与操作栏

状态栏显示：

- 图谱聚合状态。
- 已就绪文档数与总参与文档数。
- 实体、关系、事件和社区计数。
- 最后成功构建时间和图谱版本。
- 当前活动任务。

操作区包含：

- **构建待处理文档**。
- **重试失败项**。
- **全量重建**，放入更多菜单并二次确认。
- **图谱设置**。

“构建图谱”和“重建”不得在同一视觉层级并列为普通按钮，避免误触高成本操作。

### 14.3 查询与过滤

查询栏包含自然语言输入、检索策略和跳数设置。

```text
问题输入
策略：自动 / 实体 / 多跳 / 全局社区 / 时间线
跳数：1 / 2 / 3，仅实体与多跳策略显示
```

过滤区包含实体类型、来源文档和只看有证据节点。查询和过滤变化不得自动触发
高成本 LLM 请求，必须由用户提交。

### 14.4 拓扑画布

拓扑画布作为图关系探索主视图，推荐使用 Cytoscape.js 或同等成熟的 2D 图组件，
并通过动态导入避免增加知识库总览首屏体积。

画布必须遵循以下规则：

- 默认加载查询相关子图，不加载整个知识库全图。
- 默认最多 100 个节点和 200 条边。
- 节点使用实体类型颜色和一致的圆形或圆角矩形，不使用头像生成图。
- 节点标签最多两行，缩放较小时隐藏次要标签。
- 边显示关系类型，密集场景只显示选中路径标签。
- 单击节点选中并打开检视器。
- 双击节点扩展一跳邻居。
- 单击空白取消选择。
- 支持适应画布、放大、缩小、重置布局和导出当前视图 PNG。
- Hover 只提供补充信息，所有核心操作必须可点击和键盘访问。

布局优先使用稳定的层次或约束力导向布局。数据更新时保持已选节点位置，避免
整张图每次查询都剧烈跳动。

### 14.5 数据表视图

画布不是唯一信息载体。页面提供 **拓扑**、**实体**、**关系**、**事件** 和
**社区** 五个视图切换。

- **实体**：规范名、类型、描述、证据数、来源文档、更新时间。
- **关系**：起点、关系、终点、置信度、证据片段。
- **事件**：顺序、主体、动作、对象、摘要、来源。
- **社区**：层级、关键词、摘要、成员数量。

表视图支持分页、排序、过滤和深链，是无障碍与大数据量场景的基础入口。

### 14.6 实体检视器

实体检视器包含：

1. 规范名、实体类型和描述。
2. 别名和结构化属性。
3. 一跳邻居与关系。
4. 事件时间线。
5. 来源文档和证据分块。
6. **定位证据**、**编辑实体**、**合并实体** 和 **删除实体**。

编辑、合并和删除属于治理操作，必须记录审计。合并前展示受影响关系和事件数。

### 14.7 图谱查询结果

自然语言图查询结果按以下优先级展示：

1. 一句话结果摘要。
2. 关键关系路径。
3. 事件时间线或社区摘要。
4. 可验证证据分块。
5. 当前子图。

图查询结果没有证据分块时显示明确提示：

> 该结果来自图谱结构，但暂无可定位的原文证据。请谨慎用于最终回答。

### 14.8 空态与异常态

知识图谱页必须区分以下空态：

- 没有文档：引导上传文档。
- 有文档但手动策略尚未构建：提供 **构建待处理文档**。
- 所有文档被排除：解释排除规则并链接文档管理。
- 构建失败：展示失败阶段和 **重试失败项**。
- 查询无结果：建议调整实体名、策略或跳数，不建议直接重建图谱。
- 平台服务不可用：保留历史表格数据，只禁用构建与在线查询。

## 15. 测试检索与评测体验

测试检索必须让用户比较不同模式并理解系统实际使用了哪些通道，而不是只显示
一组相似度卡片。

### 15.1 测试栏

测试栏包含：

- 问题输入。
- 模式：自动、文本、图谱、融合。
- Top K。
- Rerank 开关。
- 图谱跳数，仅相关模式显示。

标准知识库禁用图谱和融合模式，并用 Tooltip 说明可通过设置升级知识库。

### 15.2 结果摘要

结果顶部显示实际执行信息：

```text
实际模式：融合
文本召回：20 → Rerank 5
图谱召回：3 个实体、4 条关系、2 个证据分块
总耗时：842ms
降级：无
```

当自动模式回退文本时，页面必须展示原因。

### 15.3 结果视图

结果使用 **综合结果**、**文本命中** 和 **图谱上下文** 三个视图。

- 综合结果按最终排序展示引用和通道徽标。
- 文本命中展示原始策略、分数和 Rerank 分数。
- 图谱上下文展示关系路径、社区和事件。
- 所有证据支持跳转分块或图谱实体。

### 15.4 评测

评测集 variant 增加：

```text
text
text+rerank
graph
fused
auto
```

除 HitRate 和 MRR 外，图谱评测至少记录：

- 关系命中率。
- 证据覆盖率。
- 无证据图事实比例。
- 图谱通道平均耗时。
- 自动路由选择准确率。

## 16. 设置页面

设置页集中承载不会频繁操作但影响索引行为的配置，避免把高风险操作散落在
多个页签。

### 16.1 基本设置

基本设置包含名称、描述和启用状态。停用知识库只影响 Agent 默认检索，不删除
文档或索引。

### 16.2 索引模式

索引模式区显示当前模式和能力对比。**切换模式** 打开独立确认流程，不直接用
Switch。

### 16.3 图谱设置

图谱增强库显示：

- 自动或手动构建策略。
- 最大跳数。
- 允许的实体类型。
- 当前图谱版本。
- **重建图谱** 和 **删除图谱数据**。

### 16.4 危险操作

危险操作区放在页面底部，包含删除图谱数据和删除知识库。

- 删除图谱数据不影响标准文本索引。
- 删除知识库删除全部文件、分块、向量和图数据。
- 删除知识库必须输入知识库名称确认。

## 17. 响应式与可访问性

响应式设计必须保持完整功能，而不是简单隐藏关键状态或操作。

### 17.1 断点

页面按以下四档验证：

| 视口 | 布局 |
|---|---|
| `>= 1440px` | 完整列表、侧边导航、右侧检视器和图谱分栏 |
| `1024px–1439px` | 压缩列宽，检视器覆盖式打开 |
| `768px–1023px` | 顶部 Tabs，列表隐藏次要列，图谱上下分区 |
| `< 768px` | 单列、全屏 Sheet、卡片化文档行、图谱以表视图优先 |

### 17.2 窄屏规则

窄屏下执行以下适配：

- 总览数据列表改为单层记录卡片，不嵌套统计卡片。
- 筛选放入可关闭的全屏 Sheet，并显示已启用筛选数量。
- 创建和上传 Modal 使用全屏 Sheet。
- 详情页侧边导航改为可横向滚动 Tabs。
- 文档三阶段状态纵向排列。
- 图谱默认打开实体或关系表，拓扑画布作为可选视图。
- 右侧检视器改为全屏抽屉。
- 固定底部操作条必须避开系统安全区域。

### 17.3 键盘与焦点

所有功能必须支持键盘操作。

- Tab 顺序与视觉顺序一致。
- 行可使用 Enter 打开，Space 只用于选择或开关。
- Modal 和 Drawer 关闭后焦点返回触发按钮。
- 图谱节点必须提供可聚焦的替代表格入口。
- 所有 icon-only 按钮必须提供 `aria-label` 和 Tooltip。
- 焦点环必须可见，不得只依赖 Hover。

### 17.4 状态播报

异步操作使用适度的 `aria-live`。

- 上传完成、任务失败和重试成功使用 `polite`。
- 会阻止继续操作的错误使用 `assertive`。
- 高频进度变化不逐百分比播报，只播报阶段变化。

### 17.5 触控与动效偏好

所有可点击目标不小于 44 × 44 像素。Hover 不作为发现操作的唯一方式。
`prefers-reduced-motion` 开启时关闭拓扑节点移动动画和平滑滚动。

## 19. 安全要求

## 20. 数据迁移与兼容

迁移必须保护现有未提交或已存在的图谱数据，并让旧客户端继续创建标准知识库。

### 20.1 Schema 迁移

生产环境使用 Alembic；开发环境可以暂时保留幂等 DDL，但必须与迁移脚本保持
同一字段定义和默认值。

迁移顺序如下：

1. 新增知识库和文档字段，设置非破坏性默认值。
2. 创建 `knowledge_index_jobs` 表和索引。
3. 回填知识库索引模式。
4. 回填文档索引状态。
5. 切换服务层策略判断。
6. 停止旧的全局自动触发逻辑。
7. 发布前端新状态与新交互。

### 20.2 现有知识库回填

回填规则如下：

- 存在图实体、关系、事件、社区，或 `graph_status != 'none'` 的知识库，设置为
  `graph_enhanced`。
- 没有任何图数据的知识库，设置为 `standard`。
- 现有图谱增强库的 `graph_build_policy` 默认设置为 `manual`，避免上线后突然
  为所有新上传文档产生模型调用。
- 管理员可在迁移后批量改为 `auto`。

### 20.3 现有文档回填

文档状态按现有数据推断：

- `parse_status=parsed` 且存在 chunk 时，`vector_status=ready`。
- 解析未完成时，`vector_status=pending` 或 `failed`。
- 标准知识库文档 `graph_status=excluded`。
- 图谱增强库中有实体或事件证据的文档 `graph_status=ready`。
- 无法确认是否完整构建的文档 `graph_status=stale`，等待增量重建。

### 20.4 API 兼容

旧创建请求继续工作并默认创建标准知识库。旧上传请求继续使用 `inherit`。旧
`/kbs/{kb_id}/graph/*` 路由至少保留一个小版本周期，并在响应头或日志中记录
弃用信息。

### 20.5 功能开关

建议增加以下发布开关：

```text
KB_INDEX_MODE_ENABLED=true
KB_INDEX_JOBS_ENABLED=true
KB_UNIFIED_RETRIEVAL_ENABLED=true
KB_GRAPH_WORKSPACE_ENABLED=true
```

开关用于灰度发布，不得形成永久的两套业务逻辑。

### 22.2 数据库与服务测试

- 创建标准库不会生成图任务。

### 22.4 检索集成测试

- 文本问题只走文本通道。

- 图谱通道证据能够回查原始 chunk。

## 24. 验收标准

以下标准全部满足后，本规格才算完成。

### 24.1 产品语义

产品语义验收确保用户看到的模式与实际运行一致。

- 创建时能明确选择标准或图谱增强知识库。
- 图谱增强明确说明包含标准检索，不产生“二选一”的误解。
- 上传默认继承知识库策略，不强迫用户重复选择。
- 标准库上传不会产生任何图谱任务。
- 图谱增强库支持自动和手动构建。
- 单文档可以排除图谱且保留文本检索。

### 24.2 状态与恢复

状态验收确保每个失败都可定位和恢复。

- 页面独立展示解析、文本索引和图谱索引状态。
- 图谱失败时文本检索仍然可用。
- 用户能看到失败阶段、原因、时间和请求 ID。
- 用户可以只重试失败阶段。
- 活动任务防止重复提交并可在刷新后继续查看。
- 部分文档失败时知识库显示“部分可用”，而不是笼统失败。

### 24.3 数据一致性

一致性验收确保图谱事实始终有有效来源。

- 替换、重新解析和删除文档后不存在无效 `chunk_id`。
- 跨文档实体不会因删除单个来源被错误移除。
- 社区在成员变化后得到更新。
- 相同内容和相同版本重复构建不会产生重复实体或关系。
- 全量重建与增量构建结果在相同输入下语义一致。

### 24.4 检索

检索验收确保知识库类型真正影响查询行为。

- 标准库只使用文本通道。
- 图谱增强库在图谱就绪时可以使用图谱或融合通道。
- 自动模式能报告实际执行模式。
- 图谱不可用时稳定降级文本并记录原因。
- 融合结果按 `chunk_id` 去重并输出统一引用。
- 对话默认只需注册和调用 `knowledge_search`。

### 24.5 UI 与交互

UI 验收确保页面专业、清晰且没有隐藏操作成本。

- 总览可按模式和健康度筛选，并快速发现失败任务。
- 创建流程清楚解释能力、适用场景、构建速度和成本差异。
- 上传前能看到将执行的流水线。
- 文档列表能直接比较三阶段状态。
- 图谱页提供拓扑与数据表，不以画布作为唯一访问方式。
- 高成本和破坏性操作具有准确的范围说明与确认。
- 所有异步按钮在执行时禁用并提供反馈。
- Hover 不造成布局位移。

### 24.6 响应式与可访问性

可用性验收覆盖桌面、触控和辅助技术。

- 375、768、1024 和 1440 像素视口无横向溢出。
- 所有触控目标不小于 44 × 44 像素。
- 普通文本对比度不低于 4.5:1。
- 所有表单有可见标签和就地错误。
- 所有核心流程可仅用键盘完成。
- 焦点状态可见，Modal 关闭后焦点正确恢复。
- 状态不只依赖颜色表达。
- reduced motion 下关闭非必要动画。

### 24.7 工程质量

工程验收证明交付不是只有界面或静态类型。

- 后端定向单元、API、数据库和检索集成测试通过。
- 前端类型检查、构建、组件测试和浏览器 E2E 通过。
- 迁移在一份生产数据副本上完成演练。
- 服务重启任务恢复测试通过。
- 审计、指标和日志能够关联 `kb_id`、`doc_id`、`job_id` 与请求 ID。

## 25. 风险与对策

本次改造同时触及数据模型、异步任务和核心页面，必须提前控制兼容和范围风险。

| 风险 | 影响 | 对策 |
|---|---|---|
| 旧知识库模式推断错误 | 上线后意外构图或隐藏历史图谱 | 根据真实图表数据回填，迁移前生成审计报告 |
| 任务状态与实际执行漂移 | 页面长期显示构建中 | 持久化任务、心跳、启动恢复和超时处理 |
| 增量删除误删共享实体 | 跨文档关系丢失 | 按证据引用计数删除，增加跨文档 fixture |
| 全量图谱渲染卡顿 | 页面不可用 | 只加载查询子图，限制节点和边，组件动态导入 |
| 两个检索工具语义冲突 | Agent 行为不稳定 | 统一 `knowledge_search`，图工具降为显式调试入口 |
| UI 状态过多难理解 | 用户仍无法判断可用性 | 三阶段流水线、聚合健康度和恢复动作统一组件 |
| 模式切换成本失控 | 大库产生大量模型调用 | 展示受影响文档和 chunk，确认后排队，支持取消 |
| Graph 平台临时关闭 | 图谱增强库不可管理 | 保留历史数据查看，文本通道继续可用 |
