# 专题一：RAG 与知识检索

## Q1.1 你们项目的 RAG 是怎么做的？为什么不用简单的 "向量检索一把梭"？

**参考答案**

本项目采用**混合检索（Hybrid Search）**策略，核心在于解决不同查询场景的匹配精度问题：

1. **向量检索**：pgvector 余弦相似度（`<=>` 算子），对语义相近、同义表述效果好；
2. **关键词检索**：pg_trgm 3-gram，对专有名词、型号、代码、报错信息这类"字面精确匹配"场景更有效（因为 embedding 对罕见词容易失真）；
3. **融合**：用 **RRF（Reciprocal Rank Fusion）** 而非加权求和的分数融合，避免不同检索通道分数量纲不一致的问题；
4. **可选精排**：接 rerank 模型对召回的候选再做交叉编码精排。

整个链路：**解析 → 分块 → 向量化 → 混合召回 → 融合 → 精排 → 注入上下文**。检索强制按 `tenant_id + enabled=true` 过滤，保证多租户数据隔离。

**面试回复模板**：

> 我们项目的 RAG 不是简单的一句话向量检索，而是标准 RAG + 混合检索的完整链路。
> 首先对文档做解析（本地解析 + 图片走 OCR 版面解析），然后按标题层级切块、表格独立成块、固定长度带重叠兜底。
> 检索上我做了混合召回：向量检索（pgvector 余弦）解决语义相似，关键词检索（pg_trgm 3-gram）解决专有名词、型号、代码这类字面精确匹配。因为 embedding 对这类罕见词经常失真，单靠向量会漏召回。
> 两路结果我用 RRF 做融合而不是加权求和，因为不同通道的分数量纲不一致，加权要调参而且不稳定。
> 再往上我加了 rerank 精排和可选的 query 改写。整个检索还做了多租户隔离的强制过滤。

## Q1.2 为什么用 RRF 而不是加权融合？RRF 的 k 值怎么理解？

**参考答案**

- **加权融合的问题**：向量分数（余弦相似度 0~1）和关键词分数（词频/TF 相关）**量纲不同**，直接加权需要调一堆超参，且对某一通道的绝对分数很敏感，容易偏科。
- **RRF 的做法**：不看绝对分数，只看**排序位置**。`score(d) = Σ 1/(k + rank_i)`，k 取 60 是业界常见默认值，作用是**削弱排名靠前项的权重差**，让排在 1、2、3 位的差异不至于太大，避免某一通道"一枝独秀"吞掉其他通道的结果。
- **好处**：归一、简单、鲁棒，各通道公平竞争，不需要跨通道调参。

**面试回复模板**：

> 融合这块我踩过加权融合的坑。因为向量分数和关键词分数的量纲根本不一样，直接 `0.6*vector + 0.4*keyword` 这种权重对通道内部的分数分布极其敏感，换个数据就得重新调参。
> 所以我换成了 RRF，它只关心每个文档在两个通道里的**排名**，`score = 1/(k+rank)`，k 取 60。这个 k 的作用是压低排名前几位之间的差异，避免某一个通道命中特别靠前就完全盖过另一个通道。这样天然归一、免调参、还稳。

## Q1.3 你们怎么做 Rerank 精排？Rerank 服务挂了怎么办？

**参考答案**

- 用 HTTP 调用 `/rerank` 端点（bge-reranker-v2-m3），有探测结果缓存（60s），避免每次打爆上游。
- **降级红线**：rerank 服务不可用时**直接返回粗排结果，绝不抛 5xx**。因为检索是查询的"生命线"，宁可精度差一点也不能让整个请求挂掉。
- 这体现了一个核心设计思想：**非关键路径组件要做优雅降级，不能因为一个可选的增强组件导致主链路失败**。

**面试回复模板**：

> Rerank 我理解它的定位是"锦上添花"，不是"雪中送炭"，所以它不能成为单点。
> 我用的是交叉编码的 rerank 模型，对召回的候选再做一次精排。对上游我做了探测结果缓存，避免频繁打挂。
> 关键的设计红线是：**rerank 服务不可用时，我直接降级返回粗排结果，绝不抛 5xx**。因为检索是整个问答的生命线，宁可精度稍微降一点，也不能因为一个可选的增强组件把整个请求干挂掉。
> 面试官，我觉得这个思想在很多系统里都通用：增强性组件要做优雅降级。

## Q1.4 你们的分块（chunking）策略是怎么设计的？为什么这么设计？

**参考答案**

- **标题层级切分**：按 Markdown 的 `#/##/###` 标题切分，保证每个 chunk 有完整语义单元（而不是被硬生生从中间切开）；
- **表格独立成块**：表格语义密集且依赖完整，单独成块避免被切开后信息断裂；
- **固定长度 + 重叠兜底**：对长文本用固定长度（默认 500 字符）+ 50 字符重叠兜底，避免语义在边界处丢失。
- 默认分块策略不是万能的，需要针对文档类型调参——这本身就是可以深入聊的优化点。

**面试回复模板**：

> 分块质量直接决定召回质量，我在这上面花了不少心思。
> 我的策略是分层的：**优先按标题层级切**，保证每个块是完整的语义单元，避免一句话被切两半；**表格单独成块**，因为表格信息密度高且依赖整体性；最后用**固定长度加重叠**兜底长文本。
> 但我也会强调，默认分块不是银弹。不同文档（技术文档、合同、代码）要调不同的 chunk size 和 overlap，这是可以持续迭代优化的点。

## Q1.5 你们还做了 Graph RAG？为什么在标准 RAG 之上还要做图谱检索？

**参考答案**

标准 RAG 擅长**事实问答**（"XX 产品的参数是多少"），但不擅长**全局性、关系性、多跳**问题（"XX 和 XX 两个系统之间怎么协作"、"公司有哪些团队负责安全"），因为这类答案分散在多个文档，向量检索难以拼起来。

Graph RAG 的价值：
1. **实体/关系/事件抽取**：LLM 从文档抽取实体、关系、事件；
2. **图扩散检索**：从实体出发，递归 CTE 做 2~3 跳扩散，能回答跨文档的多跳问题；
3. **社区发现 + 社区摘要**：两级社区发现（连通分量 + 金字塔），对全局性问题直接返回社区摘要；
4. **事件时间线**：支持"按时间排序"的事件类问题。

同时设计了**统一检索入口**：用确定性正则分类查询（`RELATION_QUERY`）判断该走文本检索还是图谱融合，图谱未就绪自动降级并记录原因。

**面试回复模板**：

> 标准 RAG 有个明显短板：它擅长单点事实问答，但回答不了跨文档、多跳的关系类问题。
> 所以我在标准 RAG 之上补了 Graph RAG。用 LLM 抽取文档里的实体、关系、事件，构建知识图谱。检索时从实体出发做多跳图扩散，再叠加社区发现和社区摘要，这样全局性问题也能答。
> 为了让两套不打架，我做了一个统一检索入口：用正则规则先判断查询类型，是关系类问题就走图谱融合，否则走文本检索，图谱没建好就自动降级到纯文本，还记录了降级原因方便排查。

## Q1.6 RAG 召回效果不好，你会怎么排查和优化？请从全链路讲。

**参考答案**

按"链路拆解"思路，从上到下逐层定位：

| 环节 | 可能问题 | 优化手段 |
|------|---------|---------|
| 文档解析 | 扫描件、表格、PDF 排版乱 | 换 OCR/版面解析 |
| 分块 | 语义被切碎 / chunk 过大 | 按标题切、调 size/overlap、小标题召回 |
| Embedding | 领域词不识别 | 换领域模型 / 微调 embedding |
| 召回 | 纯向量漏召回 | 加关键词、加混合检索 |
| 融合 | 单一通道主导 | 用 RRF、调 k |
| 精排 | 候选太多噪声 | 加 rerank、加大 top_k 再精排 |
| 上下文组装 | top_k 太大冲淡答案 | 控制注入数量、按相关度截断 |
| 评估 | 凭感觉 | 建立 HitRate@k / MRR@k + LLM-as-judge |

我们项目里专门做了 RAG 评测（evaluator）：HitRate@k / MRR@k + LLM-as-judge 的 faithfulness/relevancy 打分，并支持 baseline / hybrid / hybrid+rerank 三组变体对比——这样每次优化都能量化出"到底改好了没"。

**面试回复模板**：

> RAG 效果不好，我不会只盯着一个环节，而是全链路拆开定位。从解析、分块、embedding、召回、融合、精排、上下文组装一路排查，每层都有可能成为瓶颈。
> 比如召回差，我会先判断是"语义上没召回"还是"字面上没召回"，前者换模型，后者加关键词混合检索。
> 最重要的是**建立可量化的评测**。我们项目专门写了 RAG 评估器，用 HitRate@k、MRR@k 这种离线指标，加上 LLM-as-judge 对忠实度、相关性打分，并且支持多个方案（baseline、hybrid、hybrid+rerank）做 A/B 对比。
> 没有评测，所有的"感觉变好了"都是玄学。

# 专题二：观测体系 / 可观测性

## Q2.1 你们项目的观测体系是怎么搭建的？为什么不用现成的 LangSmith？

**参考答案**

- **为什么自建**：LangSmith 数据在云端、有隐私风险、无法深度定制、成本高，所以迁移到**本地 OpenLLMetry 体系**（traceloop-sdk + OpenTelemetry），数据落在自己的 PostgreSQL。
- **核心是 Trace 采集**：基于 LangGraph 真实事件流建立 Trace / 父子 Span 树，用 **contextvars 传播 TraceContext**（保证并发请求之间 Trace 不串）；
- **性能控制**：有界批量写入（100 条或 200ms 一事务），队列溢出按优先级丢弃（优先保留 error/timeout）；
- **脱敏管线**：删除密钥字段 → JSON Path 规则 → PII 遮罩 → 截断，且每次脱敏带 `redaction_version` 版本号；
- **内容采集模式**：`metadata_only`（默认，只存结构）/ `redacted`（脱敏摘要）/ `full`（完整内容）；
- **指标聚合**：每日/小时聚合 P50/P95/P99 延迟、Token、成本、工具调用数；
- **SLO 告警**：错误率、P95 延迟、TTFT、成本预算、质量回归等规则触发告警；
- **成本校准**：按 model_price_versions 时间生效的价格回填历史成本。

**面试回复模板**：

> 观测体系是我们比较得意的一块。一开始用 LangSmith，但它是云服务，数据在别人那、有合规风险、还不便宜，所以我自己在本地搭了一套基于 OpenTelemetry 的观测体系，数据都落在自己的数据库里。
> 核心是 Trace 采集：我基于 LangGraph 的真实事件流构建 Trace 和父子 Span，用 contextvars 来传播 Trace 上下文，这样并发请求不会串。
> 为了不影响主链路性能，我做的是**有界批量异步写入**，队列满了按优先级丢，先保 error 和 timeout。
> 还有一套**脱敏管线**，分几个阶段：删密钥字段、按 JSON Path 规则脱敏、PII 遮罩、超长截断。采集模式我分了 metadata_only / redacted / full 三档，默认只存元数据，这是对隐私很关键的设计。

---

## Q2.2 观测体系怎么做才能"不影响主链路性能"？你具体是怎么做的？

**参考答案**

观测不能拖慢业务，核心手段：
1. **异步批量写入**：不阻塞主线程，攒一批（100 条或 200ms）再写；
2. **有界队列 + 丢弃策略**：队列有上限，满了按优先级丢（error/timeout 优先保留），而不是无限堆积拖死进程；
3. **写失败重试**：指数退避重试 3 次，仍失败就放弃；
4. **采样**：根 Trace 只做一次采样决策，避免重复采样浪费；
5. **内容分级**：默认只采集 metadata，不存全量文本，从源头减负。

**面试回复模板**：

> 观测最大的坑是"观测本身成了瓶颈"。我主要从几方面控：
> 第一，**异步**，采集和上报都不阻塞主链路，攒一批批量写；
> 第二，**有界**，队列有上限，满了不是无限堆积而是按优先级丢弃，error 和 timeout 优先保留，因为这种才是要排查的；
> 第三，**失败降级**，写入失败指数退避重试三次，再不行就放弃，绝不让观测拖死业务；
> 第四，**采样和分级**，根 trace 只采样一次，内容默认只存元数据。
> 说白了，观测系统的可用性要低于业务系统，观测挂了不能影响业务。

## Q2.3 Trace 上下文在并发请求下会不会串？你怎么保证每个请求的 Trace 是隔离的？

**参考答案**

- 在 Python 里用 **`contextvars`** 存 TraceContext。注意不能用普通全局变量或线程局部变量，因为 **asyncio 单线程里协程之间会相互切换**，全局变量一定会串。
- `contextvars.ContextVar` 在每个协程上下文中是独立的，`asyncio` 原生支持 contextvars，所以 `await` 切换协程时上下文会自动正确传播。
- 同时每次请求生成唯一的 `trace_id + span_id`，写入时用 `trace_id+span_id` 作为唯一键去重，防止重复写入。

**面试回复模板**：

> 并发下 Trace 串数据是非常经典的坑。在 Python 的 asyncio 里，**千万不能用全局变量或 threading.local 存 Trace 上下文**，因为单线程里协程来回切换，全局变量铁定串。
> 我用的是 `contextvars.ContextVar`，它本身就是给 asyncio 设计的，每个协程上下文独立，`await` 切换时能正确传播。这样每个请求的 trace_id、span_id 都是隔离的。
> 另外我写入时用 trace_id+span_id 做唯一键，还能顺便做幂等去重。

## Q2.4 你怎么评估"Agent 回答得好不好"？质量怎么量化？

**参考答案**

分两部分：
1. **过程指标**：延迟（P50/P95/P99）、TTFT（首 token 时间）、Token 消耗、成本、工具调用次数、错误率——反映"跑得稳不稳、贵不贵"；
2. **结果指标**：忠实度（faithfulness）和相关性（relevancy）打分，用 **LLM-as-judge** 做 1-5 分评估（对 RAG 场景）；检索侧用 **HitRate@k / MRR@k** 离线指标。

这些统一进 SLO：错误率、P95 延迟、TTFT、成本预算、质量回归，超阈值触发告警。

**面试回复模板**：

> Agent 的质量我分成"过程"和"结果"两块看。
> 过程指标是延迟 P95、首 token 时间、Token、成本、工具调用次数、错误率，这些回答"跑得稳不稳、贵不贵"。
> 结果指标才是真正回答"答得好不好"。对 RAG 场景我用 LLM-as-judge 打忠实度和相关性的分，检索侧用 HitRate@k、MRR@k 这种离线指标。
> 最后这些都收敛到 SLO 上，超阈值就告警。比如 P95 超了、成本超预算了、质量分数掉了，都能主动发现，而不是等用户投诉。

## Q2.5 你怎么算 Agent 调用的成本？模型价格变了怎么办？

**参考答案**

- 按 Token 数和单价估算成本，但模型价格会随时间变化；
- 用 **model_price_versions** 记录"某个价格从哪个时间点生效"，成本回填时按时间查找当时生效的价格计算；
- 这样历史 Trace 的成本是准确的，不会被当前价格污染；也支持成本预算类的 SLO 告警。

**面试回复模板**：

> 成本计算有个细节：模型价格是会变的，如果拿当前价格去算历史 trace 的成本，数据就失真了。
> 我的做法是维护一个 model_price_versions，记录每个价格从什么时间开始生效。算历史成本时按 trace 的时间找到当时生效的价格再算。
> 这样既能把历史成本算准，也能支撑成本预算类的告警。

# 专题三：多 Agent 协作与编排

## Q3.1 你们的多 Agent 是怎么实现的？Agent 之间怎么通信？

**参考答案**

- 用**自研的 LangGraph Supervisor 编排架构**，不是 AutoGen 也不是 LangGraph prebuilt（保证可控可审计）；
- **通信协议**：不搞复杂的消息总线，而是用**结构化的 `TaskCard`** 作为 Agent 之间唯一交接协议（Pydantic，`extra="forbid"` 严格校验）——主 Agent 把任务拆成 TaskCard，Worker 接收 TaskCard 执行并返回结果，避免自由文本通信带来的不可解析问题；
- **编排流程**：`START → router → planner → worker(并行 Send / 顺序) → verifier → synthesizer → END`；
- 具体通信链路：
  - **Router**：基于 AgentHub 能力卡做 LLM 结构化路由，输出 `RouterDecision`（direct / orchestrate + confidence），置信度不足触发澄清；
  - **Planner**：LLM 任务分解（≤5 个任务，parallel/sequential），严格校验 target_agent 必须逐字匹配候选；
  - **Worker**：执行 TaskCard，支持重试、超时、Agent 级熔断；
  - **Verifier**：校验结果（非空/长度/拒绝标记），可一次重派；
  - **Synthesizer**：聚合多分支结果，部分失败时标注来源 Agent 综合降级。

**面试回复模板**：

> 多 Agent 我选的是自研的 Supervisor 编排，没直接用现成的多 Agent 框架，因为要保证可控、可审计。
> 最关键的设计是**通信协议**。我没有用"A 给 B 发一段自然语言"这种方式，因为自然语言不可解析、容易出错。我定义了一个严格的 `TaskCard` 结构作为 Agent 之间唯一的交接协议，字段是强校验的，谁都不能加私货。
> 整个流程是 router 先判断这个任务是直接回答还是需要编排，需要编排就交给 planner 拆解成最多 5 个并行或串行子任务，每个子任务是一个 TaskCard 分发给对应的 worker。worker 跑完结果交给 verifier 校验，不合格可能重派，最后 synthesizer 把多个结果聚合起来，部分失败也会标注出来综合成最终答案。

---

## Q3.2 Router 怎么决定"这个任务该不该分给子 Agent"？会不会误判？

**参考答案**

- Router 是 LLM 结构化路由，输出 `RouterDecision`，包含 `direct / orchestrate` 类型和 **confidence 置信度**；
- **置信度低于阈值**时不强行编排，而是触发**澄清**（反问用户），避免误分；
- 路由依据是 **AgentHub 的能力卡**（每个 Agent 的 name/description/system_prompt/scope/能力白名单），让路由有据可依而非拍脑袋；
- 用 JSON Schema 约束输出，保证可解析。

**面试回复模板**：

> Router 的设计我不只让它返回"要不要编排"，还让它返回**置信度**。因为 LLM 路由是会误判的，硬着头皮编排还不如澄清。
> 所以置信度低于阈值我就走澄清流程，反问用户到底想要什么。这样既避免了误分导致的结果混乱，也不至于动不动就问用户烦人。
> 另外我让 router 基于 AgentHub 里每个 agent 的能力卡来决策，这样它判断有依据，不是凭感觉。

---

## Q3.3 多个 Worker 并行跑，结果怎么合并？如果有的成功有的失败怎么办？

**参考答案**

- 并行用 LangGraph 的并行 Send 实现；
- 合并交给 **Synthesizer**：把多分支结果聚合，并做**降级综合**；
- **部分失败**的处理很关键：不是整个任务失败，而是**标注失败结果来自哪个 Agent**，成功部分照常输出，让用户知道哪些是可信的、哪部分失败了，可重试失败项。

**面试回复模板**：

> 并行分发我用的是图引擎的并行分支，多个 worker 同时跑。
> 关键在合并这一步，我单独做了一个 Synthesizer。它把多路结果聚合，更重要的处理是**部分失败**：我不会因为一路挂了就把整个请求干废，而是标注这一路失败是哪个 Agent 出的问题，其他成功的照常综合，最终给用户的结果里会标明哪些是成功的、哪一路失败了，方便重试和追责。

---

## Q3.4 子 Agent 会不会一直跑个不停（死循环/超时）？你怎么控制？

**参考答案**

多 Agent 系统最怕失控，控制手段：
1. **任务级超时**：每个 Worker 有执行超时，超时判失败；
2. **重试上限**：`WORKER_RETRY` 限制重试次数，防止反复横跳；
3. **Agent 级熔断**（agent_circuit_breaker）：某个 Agent 连续失败达到阈值就熔断，不再派任务给它，避免雪崩；
4. **任务数上限**：Planner 拆解任务 ≤5 个，避免无限拆分；
5. **Verifier 有限重派**：校验失败最多重派一次。

**面试回复模板**：

> 多 Agent 最怕失控，我有几道保险。
> 一是**任务超时**，每个 worker 执行有硬超时，超时就判失败，不会让它无限跑。
> 二是**重试上限**，重试次数封顶，防止它在两个 agent 之间来回踢皮球。
> 三是**Agent 级熔断**，某个 agent 连续失败达到阈值就熔断它，后续不再派任务给它，防止一个坏 agent 拖垮整个系统。
> 四是**任务数上限**，planner 最多拆 5 个任务，防止无限递归拆解。
> 层层限制下来，即使某个环节出了问题，也只会局部失败，不会全局失控。

---

## Q3.5 为什么要把"多 Agent"开关默认关掉？什么时候该用多 Agent 而不是单 Agent？

**参考答案**

- **默认关闭**：因为多 Agent 有成本高、延迟高、可靠性下降的问题——每个节点都调 LLM，编排链路长，出问题的点更多。单 Agent 已经能覆盖大部分场景，且复用主 Agent 图，更快更稳更省。
- **什么时候该用**：任务**复杂、需要多个专业角色协作**（如"既要做研究又要写代码还要复核"）、或**单一 Agent 上下文不够**（拆给不同 Agent 各管一段）时，多 Agent 才体现价值。
- 这是"**默认简单，按需复杂**"的工程哲学。

**面试回复模板**：

> 我们项目的多 Agent 开关是默认关的，这其实是个刻意的设计。
> 因为多 Agent 不是免费的：每个节点都调 LLM，成本和延迟都上去了，而且编排链路越长，出故障的点越多。
> 大部分用户问题单 Agent 就足够，我用单 Agent 还更快更省。只有当任务确实复杂、需要多个专业角色协作，或者单 Agent 上下文塞不下时，才切到多 Agent 编排。
> 我觉得这是"默认简单、按需复杂"的工程哲学，不该为了炫技就上多 Agent。

---

# 专题四：高可用 / 高并发防护

## Q4.1 你们是怎么做高并发防护的？有没有一个体系化的方案？

**参考答案**

本项目设计了一套**"限流 → 准入 → 排队 → 熔断 → 降级"五层防护栈**（L1-L5），层层递进：

- **L1 入口限流**：API Key + IP 双维度固定窗口，限流失败降级到内存；SSE 10/min、REST 60/min、IP 120/min；
- **L2 会话级单流**：`SessionStreamLock` 会话级租约（Redis + 内存 fallback，CAS Lua 脚本），保证同一会话同一时刻只有一个流，防止乱序；
- **L3 LLM 并发闸门 + SSE 排队**：`LLMGuard` 包装所有模型，提供 **online / background 双池**（对话 200 / 后台 8，后台永不挤占在线）；`StreamGate` 做 FIFO SSE 准入（有界队列 + 排队超时 + 排队位置/ETA 推送）；
- **L4 端点熔断 + AIMD + 降级模型**：错误率阈值熔断、429 自适应 AIMD、降级模型链；
- **L5 过载降级**：`DegradeController` 滞回控制器（D0/D1/D2 阶梯，高水位 0.8 / 低水位 0.7），降级时关思考、减半 max_tokens、裁剪上下文、降低 RAG top_k。

这套体系把"进来的请求"和"能扛的容量"解耦，通过排队和降级让系统在过载时**优雅劣化**而非崩溃。

**面试回复模板**：

> 高并发防护我做得比较体系化，是一个五层栈，从外到内逐层收窄。
> 第一层入口限流，按 API Key 和 IP 双维度；第二层会话级单流锁，保证同一个会话不同时跑两条流，避免回答乱序；第三层是最核心的 LLM 并发闸门，我用了 online/background 双池，在线对话请求和后台任务分开，**后台任务永远不会挤占在线体验**；同时做了 SSE 排队，告诉用户"你在第几个、大概等多久"。
> 第四层是端点熔断和 429 的自适应退避（AIMD）；第五层是过载降级控制器，水位高了自动降思考、减 token、剪上下文、降检索量。
> 这套体系的核心思想是：**系统过载时是优雅劣化，而不是直接崩掉**，把体验的牺牲控制在可接受范围。

---

## Q4.2 online/background 双池的设计思路是什么？为什么后台任务不能挤占在线请求？

**参考答案**

- **在线池（online）**：面向用户交互，要求低延迟、高优先级，默认 200 并发；
- **后台池（background）**：面向后台任务（如异步对话、记忆提炼），不要求实时，默认 8 并发；
- **隔离的意义**：如果后台任务和在线请求共用一个并发池，一旦有大量后台任务（比如批量处理文档）涌入，就会**挤占在线用户的 LLM 额度**，导致用户对话排队、体验骤降；
- 双池隔离保证**在线体验有确定的资源保障**，后台任务再忙也不影响主链路。

**面试回复模板**：

> 双池的设计是为了资源隔离，本质是**保护在线用户体验**。
> 在线池给用户交互用，要求低延迟高优先级；后台池给异步任务用，不要求实时。
> 为什么必须分开？因为如果不分开，某个时刻来了大量后台任务，比如批量建索引、批量提炼记忆，它们就会把共用的 LLM 并发额度抢光，用户的对话就被迫排队，体验直接崩。
> 用双池隔离后，**后台再忙也碰不到在线用户的资源**，在线体验就有了确定的保障。

---

## Q4.3 SSE 排队是怎么做的？用户等待时你怎么让他有感知？

**参考答案**

- 用 `StreamGate` 做 FIFO SSE 准入：有**有界队列**，超过容量就排队；
- 有**排队超时**，防止用户无限等待；
- **排队时主动推送**：告诉用户当前排队位置和预估等待时间（ETA），基于平均服务时长做指数平滑估算；
- 错误码体系区分场景：50400 槽位超时、50401 首反馈超时、50402 模型响应超时、50300 熔断打开——不同的超时原因能精准定位。

**面试回复模板**：

> SSE 排队我是有用户体验考量的，不是让用户干等。
> 超过并发容量就进一个有界 FIFO 队列，同时有排队超时兜底，不会无限等。
> 关键点是**排队时主动给用户反馈**：我会推"你前面还有 N 个、预计等待多少秒"，ETA 是用平均服务时长做的指数平滑估算，虽然不是绝对准，但能给用户预期。
> 错误码我也做了区分，槽位超时、首反馈超时、模型响应超时、熔断打开分别是不同码，这样用户报障的时候一眼就能看出卡在哪一环。

---

## Q4.4 你们怎么做熔断？和限流、降级怎么配合？

**参考答案**

- **熔断（L4）**：针对**下游（LLM 端点）**，错误率超过阈值（0.5）就打开熔断，快速失败，不再打下游，让下游恢复；配合 429 的自适应 AIMD 退避。
- **降级模型链**：熔断或失败时切换到备选模型（`LLM_FALLBACK_MODELS`），不是直接失败。
- **降级（L5）**：针对**整体系统**过载，D0/D1/D2 阶梯式牺牲体验（关思考、减 token、剪上下文）。
- 三者定位：**限流管入口，熔断管下游，降级管整体**，层层配合。

**面试回复模板**：

> 熔断、限流、降级我理解是三个不同维度的保护。
> 限流管的是**入口**，控制能进多少请求；熔断管的是**下游**，针对 LLM 端点，错误率超阈值就打开熔断、快速失败，让下游喘息恢复，配合 429 的自适应退避；降级管的是**整体系统过载**，水位高了就阶梯式牺牲体验。
> 熔断打开时我还有个兜底，就是降级模型链，会切到备用模型而不是直接失败。
> 所以它们不是孤立的，是一套：入口挡、下游护、整体扛。

---

## Q4.5 过载降级 D0/D1/D2 具体降什么？怎么避免"抖动"？

**参考答案**

- **D0/D1/D2 阶梯**：随负载升高逐级降。降级动作包括：关闭思考（reasoning）、减半 max_tokens、裁剪上下文、降低 RAG top_k——优先牺牲不影响核心答案的部分。
- **滞回控制（Hysteresis）** 避免抖动：**高水位 0.8 才升级，低水位 0.7 才降级**，中间留一个缓冲区间。如果阈值只有单点（比如 0.75 上下就切换），负载在边界波动会导致 D0→D1→D0 反复抖动，用户体验忽好忽坏。
- 用滞回区间把"升级"和"降级"的触发点错开，形成稳定的滞回环。

**面试回复模板**：

> 过载降级我用了一个滞回控制器，分 D0、D1、D2 三个阶梯。降的时候不是一刀切，是逐级牺牲：先关掉思考、减半 max_tokens、裁剪上下文、降低检索 top_k，优先保核心答案。
> 关键设计是**滞回（hysteresis）**：升级和高水位 0.8 触发，但降回 D0 要到低水位 0.7 才行，中间留缓冲带。
> 为什么必须这样？因为如果只在 0.75 一个点来回切，负载稍微波动系统就会在降级和恢复之间反复横跳，用户体验会忽好忽坏。错开触发点之后，系统在边界附近是稳定的，不会抖动。

---

## Q4.6 同一会话用户疯狂点"重新生成"，会不会打爆系统？

**参考答案**

- 会，所以有 **L2 会话级单流锁**（`SessionStreamLock`）：以 Redis 的 CAS Lua 脚本保证同一会话同一时刻只能有一个活跃流，重复请求要么排队要么被拒绝。
- Redis 不可用时降级到进程内内存锁（虽然多副本会失效，但单体部署够用）。
- 配合入口限流（SSE 10/min），即使疯狂点击也会被控制住。

**面试回复模板**：

> 这是个很真实的场景。同一会话疯狂点重新生成，如果不控制，会并发起一堆流，既浪费钱又可能回答乱序。
> 我的方案是会话级单流锁，用 Redis 的 CAS 脚本保证**同一会话同一时刻只有一个活跃流**，后续的重复请求会被拒或排队。Redis 挂了还有内存锁兜底。
> 再叠加入口限流，SSE 每分钟就 10 次，所以再怎么疯狂点也打不爆，反而会被引导到排队。

# 专题五：消息队列与异步任务

## Q5.1 你们用消息队列做什么？为什么选 RabbitMQ？

**参考答案**

- 三个场景：观测数据（span/log/audit）异步落库、会话收尾记忆提炼、ChatRun 持久化执行；
- 选 RabbitMQ 因为：功能成熟、社区大、支持 quorum 队列、死信、分级重试等可靠性机制，且这套系统已经有 Redis 做缓存，MQ 独立出来职责清晰。

**面试回复模板**：

> 消息队列我主要承接三类异步任务：观测数据的批量落库、会话收尾的记忆提炼、以及持久化 ChatRun 的执行。
> 选 RabbitMQ 是因为它可靠性机制完整，支持 quorum 队列、死信队列、分级重试这些，而且它跟 Redis 职责分离，一个做缓存一个做异步解耦。

---

## Q5.2 异步任务的可靠性怎么做？消息会不会丢？会不会重复消费？

**参考答案**

- **不丢**：
  - quorum 队列（镜像/持久化，节点挂不丢）；
  - **手动 ack**：消费成功才 ack，失败不 ack 触发重投；
  - **非阻塞 confirm 发布**，发布失败走降级路径；
- **不重复**：
  - 消费者侧**幂等去重**（`dedupe.py`，按消息唯一键），配合手动 ack，即使重投也不重复处理；
  - 会话收尾、ChatRun 领取等关键操作也做幂等（DB 唯一约束）。
- **失败重试**：**分级重试队列**（TTL 5000/30000/120000ms 递增），重试次数递增；超限进**死信队列（DLX）** 供人工排查。

**面试回复模板**：

> 异步任务可靠性我主要回答两个问题：不丢和不重复。
> 不丢靠三样：quorum 队列持久化（节点挂都不丢）、手动 ack（处理成功才 ack，失败会重投）、发布端 confirm（发布失败有降级路径）。
> 不重复靠**幂等去重**，消费者按消息唯一键去重，这样即使 MQ 重投一条消息，我这边也不会重复处理。
> 失败重试我是**分级重试**，TTL 按 5 秒、30 秒、2 分钟递增，越失败等越久；超过最大次数就进死信队列，单独捞出来排查，不会无限重试污染主队列。

---

## Q5.3 你们怎么实现多个 Worker 之间"同一任务只被一个处理、且能恢复"？

**参考答案**

以 ChatRun（持久化对话执行）为例，用**数据库租约（DB lease）机制**实现分布式任务协调，不用分布式锁：

1. **租约领取**：Worker 用一条 SQL（带唯一约束/乐观锁）原子地把任务标记为"被自己认领"，带上租约到期时间；
2. **心跳续约**：处理过程中周期性地续约，证明自己还活着；
3. **过期恢复**：如果 Worker 崩溃没续约，租约到期后任务被释放，其他 Worker 可以重新领取；
4. **幂等**：领取基于唯一约束，保证同一时刻只有一个 Worker 能拿到，重复领取会被数据库拒绝。

这比依赖外部分布式锁更简单、更可靠，直接利用数据库的一致性。

**面试回复模板**：

> 多个 Worker 抢同一个任务，我不引入额外的分布式锁，而是用**数据库租约**，更简单也更可靠。
> 领取任务时用一条带唯一约束的 SQL 原子操作，谁先拿到就把任务标记成自己的，同时带上租约到期时间，数据库的唯一约束保证了同一时刻只有一个 Worker 能拿到。
> 处理过程中 Worker 周期**心跳续约**，证明自己还活着。如果某个 Worker 崩溃了没续约，租约到期后任务就被释放，别的 Worker 可以重新领走，这样就实现了故障恢复。
> 这个方案的好处是不用维护一套分布式锁组件，直接用数据库的一致性就搞定了。

---

## Q5.4 为什么观测数据的写入要走 MQ 而不是直接写库？

**参考答案**

- **解耦与削峰**：观测数据量大且突发，直接写库会把数据库打爆，MQ 缓冲削峰；
- **不阻塞主链路**：Trace 采集是高频事件，同步写库会拖慢请求，MQ 异步化让主链路快速返回；
- **批量 + 幂等**：消费者批量攒着写、按唯一键去重，写库更高效。
- 本质是"**高频低价值的观测数据和低频高价值的业务请求分离**"。

**面试回复模板**：

> 观测数据的特点是**量大、突发、低价值**，它和业务请求完全不是一种负载。直接同步写库，一来会把数据库打爆，二来会拖慢主请求。
> 走 MQ 之后有三好处：一是**削峰**，观测数据再多也只是积压在队列里，不会冲击数据库；二是**解耦**，主链路发完消息就返回，不关心落库是否成功；三是消费者能**批量+幂等**地写库，更高效。
> 核心思路就是把"高频低价值的观测数据"和"低频高价值的业务请求"彻底分离，不能让观测拖累业务。

# 专题六：缓存设计

## Q6.1 你们做了语义缓存？为什么用语义相似度而不是精确匹配？

**参考答案**

- 用户问同一类问题，表达可能完全不同（"帮我总结这篇文档" vs "这篇文档讲了啥"），**精确匹配命中率极低**，所以用**语义相似度**（BGE-M3 embedding，默认阈值 0.95）来判断是否命中缓存；
- 命中后直接返回历史结果，省一次 LLM 调用，降成本降延迟。

**面试回复模板**：

> 精确匹配在问答场景基本没用，因为用户换个说法就问不到缓存了，比如"帮我总结这篇文档"和"这篇文档讲了啥"其实是同一个问题。
> 所以缓存我用了**语义相似度**，把 query 向量化，跟缓存里的历史 query 比相似度，超过阈值（0.95）就算命中，直接返回历史结果，省一次 LLM 调用。
> 这样既降成本又降延迟。

---

## Q6.2 语义缓存会不会"误命中"导致答错？你们怎么控制风险？

**参考答案**

这是语义缓存最危险的地方——**答错比答得慢更严重**。控制手段：

1. **保守阈值**：相似度阈值设得很高（0.95），宁可少命中也不误命中；
2. **四维隔离**：按 `tenant/user/agent/model` 四个维度隔离，不同用户、不同 Agent、不同模型不共享缓存，避免串上下文；
3. **正则拦截**：用正则**保守地拦截**三类不该缓存的问题——
   - **工具动作**（"帮我执行/创建/删除"）：有副作用，绝不返回缓存；
   - **时效信息**（"今天天气/最新价格"）：缓存会过期答错；
   - **对话上下文依赖**（"那它呢"）：脱离上下文无法回答；
4. **工具调用绝不写入缓存**：因为工具执行结果可能随时变化（查了数据库），缓存会给出过期结果。

**面试回复模板**：

> 语义缓存最大的风险就是**误命中导致答错**，而答错比答得慢严重得多。我从几个层面控风险。
> 一是**阈值保守**，0.95 这个阈值很严，宁可少命中也不误命中。
> 二是**四维隔离**，按租户、用户、Agent、模型四个维度隔离，不同上下文不共享，防止串味。
> 三是**正则拦截**，我会保守地拦掉三类问题：有副作用的工具动作、有时效性的信息、依赖对话上下文的指代。这些都不该走缓存。
> 四是**工具调用结果绝不写入缓存**，因为它可能随时变。宁可牺牲缓存命中率，也要保证**绝不答错**。

---

## Q6.3 语义缓存放哪里？Redis 挂了怎么办？

**参考答案**

- 主存储用 **Redis**（TTL 存储，性能好、支持过期）；
- Redis 不可用时**降级到进程内缓存**，保证功能可用（多副本下会有一定不一致，但单体部署可接受）；
- 这也是整个系统"**Redis 是增强，PG 是底线**"思路的体现——缓存是可牺牲的，核心数据落 PG。

**面试回复模板**：

> 语义缓存主存储用 Redis，因为性能好还支持 TTL 过期。
> Redis 挂了我会降级到进程内内存缓存，保证功能不挂。当然多副本部署下内存缓存会不一致，但单体场景完全够用。
> 这也符合我们整个系统的思路：**Redis 是增强不是底线**，缓存可以牺牲，核心数据必须落在 PostgreSQL 上。

# 专题七：安全与多租户

## Q7.1 你们怎么做 API Key 校验？如何防时序攻击？

**参考答案**

- API Key 哈希后存储，校验时对哈希做比较；
- 用**常量时间比较**（constant-time comparison），避免攻击者通过比较耗时差异逐个猜字符（时序攻击）；
- 同时 API Key 哈希存储，数据库泄露也拿不到明文。

**面试回复模板**：

> API Key 我做了两件事：一是**哈希存储**，数据库存的是哈希不是明文，即使库泄露也拿不到原始 Key。
> 二是校验时用**常量时间比较**，不能用普通的 `==` 逐字符比较。因为普通比较一旦遇到不匹配的字符就提前返回，比较耗时会泄露"前缀对了几个"的信息，攻击者能据此逐位爆破。常量时间比较保证无论是否匹配耗时都一样，从根本上堵住时序攻击。

---

## Q7.2 你们怎么做多租户数据隔离？哪些地方容易漏？

**参考答案**

- 租户通过 `X-Tenant-Id` 标识（当前直接受信任，非生产级 RBAC）；
- **所有 SQL 强制 `tenant_id` 过滤**（检索、记忆、图谱、会话等），这是最核心的红线；
- 最容易漏的地方：**缓存**（所以语义缓存做四维隔离含 tenant）、**后台任务**（Worker 处理数据时必须带上 tenant）、**观测数据**（Trace 也要按租户隔离）、**索引/聚合**（跨租户聚合会泄露）。

**面试回复模板**：

> 多租户隔离，我强调的是**"所有数据访问路径必须强制带租户过滤"**，这是不能靠自觉的红线。
> 最基础的是所有 SQL 强制 tenant_id 过滤。但真正容易漏的是那些"隐性"的数据路径：
> 一个是**缓存**，所以我的语义缓存专门做了租户维度隔离；
> 一个是**后台任务**，Worker 异步处理数据时如果丢了租户上下文就会串；
> 一个是**观测数据**，Trace 日志也要按租户隔离；
> 还有**聚合索引**，跨租户聚合就是泄露。
> 我自己会专门做一次"租户泄露"的安全审查，把所有数据流动路径都过一遍。

---

## Q7.3 观测系统里可能采集到敏感数据（PII），你怎么处理？

**参考答案**

- 观测脱敏管线：**删除密钥字段 → JSON Path 规则 → PII 遮罩 → 截断**，并且每次脱敏带 `redaction_version` 版本号（未来脱敏规则升级可以追溯）；
- **内容采集分级**：默认 `metadata_only`（只存结构指标），`redacted`（脱敏摘要），`full`（完整内容）——默认不存全量，从源头降低敏感数据暴露。

**面试回复模板**：

> 观测系统很矛盾：既要采集足够信息排查问题，又不能把用户的敏感数据存进去。
> 我做了一条脱敏管线，分几阶段：先删密钥字段，再按 JSON Path 规则脱敏，然后做 PII 遮罩，最后超长截断。而且每次脱敏都带版本号，将来规则升级了能追溯。
> 更关键的是**内容分级**：默认只存元数据（metadata_only），不存完整对话；只有显式需要排查时才用脱敏摘要档。默认不采集全量内容，从源头就把敏感数据暴露降到最低。

# 专题八：系统设计场景题

## Q8.1 如果用户量翻 10 倍，这个系统会先挂在哪里？你怎么扩容？

**参考答案**

结合本项目已知的边界来答：

1. **最先挂的**：当前**并发闸门/熔断是进程内状态**（LLMGuard、StreamGate、内存锁都在单进程内），多副本部署后这些防护会失效——流量进来挡不住，最先崩；
2. **其次**：数据库（PG 承担了向量、图谱、观测、业务全量数据，负载最重）；
3. **扩容方案**：
   - 先把**闸门、熔断、单流锁、语义缓存迁移到 Redis**，让防护变成分布式共享状态；
   - 数据库**读写分离 + 冷热分层**，观测数据量大、价值低，独立库/独立表分区；
   - 观测 Worker 独立扩副本；
   - LLM 调用是无状态的，backend 可以横向扩，前提是防护状态已迁到 Redis。

**面试回复模板**：

> 如果流量翻 10 倍，我能很明确地说出最先崩的地方：**并发防护是进程内的**。我们的 LLM 闸门、SSE 排队、单流锁目前都在单进程内存里，单体部署没问题，但一多副本就失效了——流量一上来，防护挡不住，直接被打穿。
> 所以要扩容，第一步是把这些状态**迁移到 Redis**：闸门、熔断、单流锁、语义缓存全部做成分布式共享。
> 第二步是数据库，PG 现在扛了向量、图谱、观测、业务全部负载，需要读写分离和冷热分层，观测这种大而低价值的数据单独隔离。
> 第三步，LLM 调用本身无状态，backend 可以放心横向扩。整体思路就是：**先让防护状态分布式化，再横向扩无状态服务，最后解耦数据库**。

## Q8.2 一次 Agent 请求很慢，你怎么定位瓶颈在哪个环节？

**参考答案**

靠观测体系的 Trace：
1. 打开这个请求的 **Trace**，看 Span 树——是 LLM 调用慢、工具执行慢、还是检索慢、排队慢；
2. 看指标：TTFT（首 token）、P50/P95 延迟分布；
3. 看是否**排队**（StreamGate 的排队时长）、是否**熔断降级**、是否**缓存未命中**走了全量 LLM；
4. 看是偶发还是常态——偶发看采样和错误 Trace，常态看聚合指标和 SLO 告警。

**面试回复模板**：

> 定位慢请求，我直接靠观测体系，不靠猜。
> 先拉这条请求的 Trace，看它的 Span 树，能精确到是 LLM 调用慢、工具执行慢、检索慢，还是进来就排队了。
> 再看几个关键指标，首 token 时间、P95 延迟。如果慢在排队，那是并发容量问题；如果慢在 LLM，那是模型或降级模型的问题；如果慢在工具，那是下游依赖问题。
> 最后区分偶发还是常态：偶发就翻错误 Trace，常态就看聚合指标和 SLO 告警。整套下来，瓶颈定位基本是分钟级的，不用猜。

## Q8.3 怎么保证 Agent 系统上线后"不会乱说"（幻觉/失控）？有没有兜底？

**参考答案**

- **约束来源**：RAG 限定回答来源（忠实度评估）、Graph RAG 提供结构化事实、系统提示词严格约束角色和行为；
- **HITL（人在回路）审批**：对高风险工具调用（写入、删除、对外操作）设置**人工审批节点**（`GRAPH_INTERRUPT_TOOLS`），工具执行前暂停等人工确认；
- **工具白名单**：Agent 只能调用声明允许的工具（能力白名单），不能任意执行；
- **质量评估**：LLM-as-judge 对输出打忠实度/相关性分，超阈值告警；
- **观测兜底**：所有工具调用、决策全程留痕可审计，出问题可回溯。

**面试回复模板**：

> 让 Agent 不乱说，我是多管齐下。
> 一是**约束信息来源**，RAG 和 Graph RAG 让答案有出处，配忠实度评估。
> 二是**高风险操作人工审批**，对有副作用的工具调用（写入、删除、对外发消息）设置了 HITL 审批节点，执行前必须人工确认，这个默认是关的，但对高风险场景会打开。
> 三是**工具白名单**，Agent 只能调用允许的能力，不能乱执行。
> 四是**全程留痕**，所有决策、工具调用都进观测和审计日志，真出问题能精确回溯。
> 说白了，Agent 的能力边界要受控，关键动作要人在回路，全程可审计。

## Q8.4 如果 LLM 上游服务挂了（比如限流、报错），你们的系统怎么保证不雪崩？

**参考答案**

多层兜底：
1. **端点熔断**：LLM 错误率超阈值，熔断打开，快速失败，不再猛打上游；
2. **429 自适应 AIMD**：收到限流，自适应退避，减并发，不硬刚；
3. **降级模型链**：主模型挂，自动切备选模型；
4. **语义缓存**：同类问题直接命中缓存，根本不调 LLM；
5. **五层防护**：限流、排队把对上游的压力控制在容量内。

**面试回复模板**：

> 上游 LLM 挂了是最常见的故障，我分几层防雪崩。
> 第一，**端点熔断**，错误率超阈值直接打开熔断，快速失败，给上游喘息时间。
> 第二，**自适应退避**，收到 429 限流信号就 AIMD 退避，减少并发，不去硬刚。
> 第三，**降级模型链**，主模型挂自动切备用模型。
> 第四，**语义缓存**，同类问题直接命中缓存，压根不调 LLM。
> 再加上五层防护栈整体的限流和排队。所以上游即便全挂，我的系统是**优雅降级**而不是跟着一起崩。

## Q9.1 你觉得这个项目离生产上线还差哪些？最大的短板是什么？

> 我承认短板不是坏事，反而说明我知道生产化的改造路径在哪。这些我都想清楚了怎么改。

## Q9.2 让你从零再做一个类似的 Agent 平台，哪些设计你会保留，哪些会推翻？

**参考答案**

- **会保留**：五层并发防护的**思想**（可迁移到 Redis）、语义缓存的"保守防错"哲学、混合检索 + RRF、观测脱敏管线、TaskCard 强协议的多 Agent、数据库租约做分布式任务。
- **会推翻/重构**：
  - 数据库**选型**：PG 扛了太多职责（向量、图谱、观测、业务），生产会考虑向量单独用 Milvus/Weaviate，观测用 ClickHouse 或专用 APM；
  - **鉴权从零设计**：直接上企业认证 + RBAC，而不是后补；
  - **进程内状态**：一开始就把防护状态设计成可分布式（Redis），避免后置迁移；
  - **建表**：一开始就用 Alembic 迁移，而不是自动建表。

**面试回复模板**：

> 让我重做一遍，我会保留的是那些"**思想层面的设计**"：五层防护的分层思想（只是状态要一开始就放 Redis）、语义缓存"宁可少命中也不答错"的保守哲学、混合检索加 RRF、观测脱敏管线、用强类型 TaskCard 做多 Agent 通信、数据库租约做分布式任务。这些是通用且正确的。
> 会推翻的是几处**地基**：
> 第一，数据库职责要拆分，不能让 PG 同时扛向量、图谱、观测、业务，观测这种大而低价值的数据应该用专门存储；
> 第二，**鉴权从第一天就设计**，直接接企业认证和 RBAC，而不是后补；
> 第三，**进程内状态一开始就做成分布式的**，避免后面再迁移；
> 第四，建表用正式迁移工具。
> 说白了，思想和算法层是成熟的，但基础设施的选型我会重新做更合理的决策。

## Q9.3 项目里哪些地方用到了 AI Agent SDK（CodeBuddy Agent SDK）？它和 LangGraph 是什么关系？

**参考答案**

- 项目底层用了 **LangGraph** 作为 Agent 运行时（ReAct 循环：agent 节点 + tools 节点）；
- 同时集成 **CodeBuddy Agent SDK**（`@tencent-ai/agent-sdk`）的能力，用于单次/多轮对话封装、Agent 调用、工具权限控制等；
- 二者是**不同层次的抽象**：LangGraph 提供图编排和状态机底层能力；Agent SDK 提供更高层的对话、会话、Agent 封装，方便业务层调用。
- 可以用 **Agent SDK 的 Query/Session API** 快速接入，用 **LangGraph** 做精细的流程编排，两者互补。

**面试回复模板**：

> 项目里 LangGraph 是核心的 Agent 运行时，提供图编排、状态机、Checkpoint 这些底层能力，我的 ReAct 循环、Supervisor 编排都是基于它画的。
> 同时我也用了 CodeBuddy Agent SDK，它提供更高层的封装，比如单次对话的 Query API、多轮会话的 Session API、Agent 管理和工具权限控制，业务层接入更方便。
> 两者的关系是**不同抽象层次**：LangGraph 是引擎、拼的是流程和状态；Agent SDK 是接口、拼的是对话和会话能力。需要精细控制用 LangGraph，需要快速接入用 SDK，二者是互补的，不是二选一。
